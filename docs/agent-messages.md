# Agent messages and sending into sessions

Agent HUD can put words into a running Claude Code, Codex, Antigravity or DeepSeek Harness session, hand them to a Cursor, TRAE, WorkBuddy, ZCode, Qoder or Kimi Code session when one of its turns ends, or to an open Pi or OpenCode session once it is idle, and start a new Claude Code, Codex, Antigravity, DeepSeek Harness, Pi or OpenCode session. On top of that, agent messages let one agent session message, start and read another through Agent HUD's MCP server.

## Keep approvals in the client

In Agent HUD 0.6.7 on macOS, open **Settings → Agents**. Under **Agent tools**, turn on **Let agents message each other**. Then choose the client that should handle its own approvals.

- Under **OpenAI → Codex CLI**, turn off **Answer in the HUD**. **Messages** still shows **On**.
- Under **Anthropic → Claude Code CLI**, turn off **Answer in the HUD** and leave **Send messages** on. **Answer questions** is unavailable while **Answer in the HUD** is off.

If you use Claude Desktop and turn off only **Answer questions**, you may still see a next-step question on the HUD. Answer it in Claude Desktop. **Dismiss** hides the card and leaves the question open in Claude.

If the HUD says “This request is no longer waiting” after you answer elsewhere, check the result in the client that handled it. The HUD only accepts answers for requests it still has open.

To check your setup, send a message between two sessions connected to Agent HUD's MCP server. Have the recipient reply with `send_message` and the original message ID in `reply_to`. The reply should arrive as a new turn in the sender's session. With Codex CLI 0.170.0 on macOS, this worked with client hooks uninstalled, and a file write in a read-only session still waited for **Yes, proceed** in Codex.

## Where the code lives

- `src/crates/platform/src/delivery/` (`agent_hud_platform::delivery`): sending into sessions (`LocalClients`, `Receipt`, `DeliveryState`), starting sessions (`SessionStarts`, `StartConfig`) and moving started Claude jobs into the desktop app (`Handoffs`). The `fixtures` cargo feature exposes `delivery::fixtures` to other crates' tests.
- `src/crates/messaging/` (crate `agent-hud-messaging`): the agent messages tool group (`Messaging`), its journal, the reading of answers and the paper plane (`Flight`).
- `src/crates/host/src/messages.rs` (`AgentMessages`): the host's owner of the group.
- Settings: `src/packages/app/src/settings/agent-plugins/AgentMessagesRow.tsx` and the "Send messages" switch on a client's page (`src/packages/app/src/settings/agents/ClientFeatures.tsx`). The relay's side is in [the MCP app](../src/apps/mcp/README.md).

## Sending into a session

`LocalClients` is one synchronous owner per app; share its `Arc` rather than making a second one. A gate per session keeps that session's sends in order without holding up other sessions. Its calls block, so a GUI host runs them off the UI thread. The host hands it the main sessions it already knows (`update_targets`). Making one scans no transcript, installs nothing, changes no client setting and launches no app.

- **Request ids** are the caller's and stay the same for one attempt (letters, digits, `-` and `_`, at most 128 bytes); the client sees `agent-hud:<id>`.
- **Journal.** Before anything is sent, a file in the receipts folder records a SHA-256 fingerprint of the request and an `uncertain` receipt, never the words. The same id again returns that attempt; the same id with other words or options fails.
- **No blind retries.** Once bytes may have left, a timeout, a disconnect, an unreadable acknowledgement or a crash leaves the receipt `uncertain`. Nothing is sent again, through the same owner or another.
- **Receipts** keep the session and thread ids, both request ids, and the turn and Desktop owner when known; `known_receipts` gives the last 7 days. `delivered` and `started` note which of Agent HUD's surfaces sent a prompt, so the session's tags name the sender and not the app that took it.

### Claude Code

Through Agent HUD's Claude Code plugin (`src/crates/platform/src/claude_plugin`), installed from its page in Settings → Agents. Every session running it checks in to the folder it shares with the app every 5 seconds; a check-in counts for 20 seconds. A send is left in that folder, and the plugin claims it before calling `$.prompt.submit`. The words wait for the session to go idle while check-ins go on, and the receipt reads taken, started or refused.

- Only automatic and enqueue sends; slash commands are refused. Words nobody claimed within an hour expire.
- Cancelling is a request until the plugin acknowledges it; words already taken cannot be promised withdrawn.
- `maintain` captures the plugin's last states before it removes taken files a minute later. It is housekeeping, not a collector.
- "Send messages" on the plugin's row (`claudeMessages`, on by default) decides whether any message from Agent HUD goes into a Claude Code session. Senders check it and refuse with `delivery::CLAUDE_MESSAGES_OFF`.

### Codex

- **Desktop owner first.** Automatic, start, steer and interrupt sends go to the Codex desktop app that owns the thread. Only a proven absence of that owner, before anything is written, lets a send try the command line: a thread loaded in a live TUI, reached through Codex's shared daemon. It never runs `codex -p`, resumes the thread in another engine or opens a second TUI. Its thread state is read at stream version 11 or 13 (Codex in ChatGPT.app 157 sends 13).
- An automatic send reads the thread's running state and makes one start or steer. A steer names the turn it expects, or none: then it goes into the turn in progress when the owner is asked, and with no turn in progress it is refused (`delivery::NO_TURN_TO_STEER`) before anything is written. A command-line interrupt names the exact turn. The desktop owner has no interrupt, and accepted input cannot be withdrawn.
- **Enqueue** (what agent messages use unless they steer) puts the words into Codex's shared queue (`thread/queue/add`) without loading the thread: through the shared daemon when one runs, else through a short-lived `codex app-server` started from the host's `QueueRoute` (`StartConfig::codex_queue`). Whichever app has the thread open sends the item as a new turn once the thread is idle, so it never steers or interrupts. The receipt is `queued` with no turn; the turn is found later by its `agent-hud:<id>`.
- An app holds `thread-writer-locks/<thread>.lock` in Codex's folder while it has the thread loaded (`codex_thread_open` asks without waiting). When no app holds it and Codex's desktop app (Codex.app or ChatGPT.app) is installed, the host opens `codex://threads/wake/<thread>`; otherwise the item waits until a Codex opens the thread.
- Desktop apps are looked for only on macOS (`/Applications`, `~/Applications`). On Windows, Codex takes desktop start, steer and automatic sends and the queue (through the short-lived app-server), without command-line owner control or interrupt.

### Antigravity

Through the running Antigravity local language server: enqueue delivers when the session is idle, steer at the next invocation, and interrupt cancels the cascade. Whether the server is there is found out at submission, so `reachable` stays null until then. The route is verified on macOS and unverified on Linux; on Windows it sends into existing sessions but cannot interrupt or start one. There a message goes to a service that has the conversation loaded (`GetAllCascadeTrajectories`), else to the first that opens it when asked for the steps past its last (`GetCascadeTrajectorySteps` with `stepOffset` 2³²−1: `{}`, or not_found from a service that cannot find it), so a long conversation is never read whole to be found.

### DeepSeek Harness

Through Agent HUD's DeepSeek Harness plugin (`src/crates/platform/src/deepseek_plugin`), with the Claude Code plugin's protocol over `deepseek-channel` in the app's data folder (`LocalClients::with_deepseek_channel`; without it no Harness session takes a message). A session that checked in within 20 seconds takes automatic, enqueue and steer sends; slash commands are refused. The plugin hands each prompt to Harness's session controller with `mode: 'queue'`, so it joins the session's own queue and never interrupts a turn; the file then says taken, started (Harness queued it) or refused. A steer (channel version 3; `mode: "steer"` in its file, taken only within `STEER_LIFETIME`, 8 seconds) goes to the controller with `mode: 'steer'`, which puts it before the next step of the turn in progress. Harness's steer starts a turn when none runs, so the plugin refuses it first when the session's agent is not running (`NO_TURN_TO_STEER`) or waits on an approval or a question it asked; it names no turn ahead and takes no model. The file then names the turn it went into (`steeredInto`, Harness's turn number); one whose turn ended or changed while Harness took it names none, and the send is `uncertain`. The app waits for that answer before it returns, and one the plugin never took is dropped once its lifetime ends.

The snapshot names a Harness session `deepseek:session-<uuid>`; Harness, its plugin and the relay's caller name it `session-<uuid>`. Both are taken. "Send messages" on the plugin's row (`deepseekMessages`, on by default) decides whether any message goes into a Harness session (`delivery::DEEPSEEK_MESSAGES_OFF`). A new Harness session is started through the same plugin (see Starts below).

### Cursor, TRAE, WorkBuddy, ZCode, Qoder and Kimi Code

Through the session's own completion hook, the only route these clients support, and in Qoder CLI also its rewake hook (`docs/client-hooks.md`). A send is left in the `hook-channel` folder of the receipts folder under `<client>--<session>`; when the session's `Stop` (Cursor: `stop`) hook fires, it claims the oldest message and replies with it in the client's own continuation form, so the client takes it as the next input and carries the turn on. The receipt reads waiting until then, started after. A message a session has not taken within an hour expires.

- Only automatic and enqueue sends; slash commands are refused, and so is a ZCode message over 24,000 characters (ZCode cuts hook text there).
- Not on Windows yet. How each of these clients starts a hook command there is unverified, so Agent HUD writes none of their hooks on Windows: their sessions can send with the MCP server but cannot receive, and `list_sessions` reports them not reachable (Open #89), saying that Agent HUD puts no hooks in for them on this system yet; Settings says the same on each client's row, rather than a bare "No hooks" that reads as a setup gone wrong (Open #115).
- A turn is carried on only as often as the client allows; the rest wait for a later stop. WorkBuddy and CodeBuddy set no cap and Agent HUD adds none, so there only the limit on passes between agents ends a chain.
- An idle session takes nothing until its next turn ends, except in Qoder CLI: there Agent HUD's rewake hook waits in an interactive session from its start and from each turn's end, and hands a message over at once, so the idle session answers it (`docs/client-hooks.md`). `list_sessions` says which: reachable `true` while a turn runs or a rewake hook waits, `null` for another idle session, and `false` until its client's hooks have reported to Agent HUD (`hooks.at` on the session, for this session or another of the same client in the last week). TRAE runs hooks only once its global hooks are on (TRAE Settings → Hooks).
- Their agents send with Agent HUD's MCP server in each client's own settings file. WorkBuddy starts a server from `~/.workbuddy/mcp.json` only after the user trusts it once (Connectors → Custom connectors); TRAE splits a server's `command` at its spaces unless it is in double quotes, so Agent HUD writes its path quoted there.
- The follow-up the hook notes names the message it handed over (`delivered`), which is how `get_message` finds its turn when the client keeps no readable log (TRAE, Cursor): the answer is the reply the next completion reports, its first 40 KB. Cursor's `stop` carries no reply, so it is read from the end of the transcript the hook names: the last assistant text after the turn's prompt, never an older turn's.
- Agent HUD sees only a session's latest turn of these clients, so the answer read when its plane is thrown back is kept in memory, never in the message log (`answers.rs`, the newest 64): `get_message` still gives it after the session's next turn ends, until Agent HUD restarts. Live facts that name the message as the turn that ended count even while the session's next turn runs.

### Pi and OpenCode

Through Agent HUD's own observer in the client: Pi's extension and OpenCode's plugin, both OpenCode 1's and OpenCode 2's (`docs/client-hooks.md`), carry a mailbox (`src/crates/agents/src/hooks/mailbox.js`), with the path of the app's `hook-channel` written in when Agent HUD installs them (`Clients::with_channel`; Oh My Pi, Kilo Code and MiMo Code get none). A send waits under `prompts/<client>--<session>` as for the hook clients above, and the observer claims it the same way (`ClaudeChannel::take_next`).

- An open session takes a message once it is idle: Pi when its run settles (`agent_settled`) or within two seconds, as `pi.sendUserMessage`; OpenCode within two seconds. OpenCode 1 takes it as `session.promptAsync` with the model and agent of the session's newest prompt, as OpenCode itself resumes a session (without them OpenCode runs it on the agent's default model). OpenCode 2 takes it as `session.prompt`, queued, which runs on the session's own agent and model: only into a main session of the folder that copy of the plugin serves (OpenCode 2 loads the plugin once for each folder its background service serves), while no execution runs in it (its `time.busy` is not after its `time.idle`) and no undo is pending. Both versions run one look (`handOver` in `observer.js`). A message that comes while a turn runs waits for its end.
- One message goes to one session once: the claim beside it lets only one process or copy of the plugin take it, and under OpenCode 2 the copies of one process also share which sessions have a message on the way, so two copies serving one folder never hand the same session two at once.
- While its process runs, each observer says which sessions it holds (`observers/<client>@<pid>-<instance>.json`, every 20 seconds in Pi, every 30 in OpenCode, which lists its server's main sessions, or under OpenCode 2 the main sessions of the copy's folder). `list_sessions` says reachable `true` for a session an observer named in the last 75 seconds from a process that still runs, `null` otherwise (`hooks::mailbox::standing`): an OpenCode 2 session is open while the background service serves its folder. An observer removes the file of a process that is gone, and an OpenCode 2 copy its own when OpenCode unloads it.
- The turn's record names the message (`delivered`) and carries the reply's text, its first 40,000 characters, which `get_message` returns; a turn that took a message and failed or was stopped is recorded as ended, so its message is done without an answer. OpenCode 2 marks the prompt with the message's id (`metadata.agentHud.message`) and names the message by the marked prompt among those since the session last went idle, so each copy of the plugin records the same turn; an execution stopped by OpenCode shutting down ends no turn, since it resumes when OpenCode starts again. As for the hook clients above, the answer is kept in memory once read.
- OpenCode 2's plugin does not note calls of Agent HUD's MCP tools yet (OpenCode 1's does, in `tool.execute.before`), so Agent HUD knows no OpenCode 2 session as a sender, and a message an OpenCode 2 session sends is refused (see Sender below).
- Only automatic and enqueue sends; slash commands are refused. Pi and OpenCode read Agent HUD's MCP server from `~/.pi/agent/mcp.json` and the `mcp` key of `~/.config/opencode/opencode.json`, and its skill from `~/.agents/skills` (OpenCode also reads `~/.claude/skills`, so a second copy there is a duplicate it warns of).

## Starting sessions

`SessionStarts` starts a session with a first prompt, which cannot begin with `/`, in a folder offered from existing sessions (`offers_for`: per client, the ten latest project folders that still exist and that its workspace trust accepts) or with no project in `~/.agenthud/sessions/<client>/<request>`, whose Claude Code folder is marked trusted in Claude Code's settings first. A client is offered when its command line is found (Antigravity also when its desktop app is installed); Pi's and OpenCode's are looked for at every offer and start (`pi`, `opencode`, also `~/.opencode/bin` and the `opencode-cli` OpenCode's desktop app carries, and on Windows npm's `.cmd` shims). Starts have their own request ids, fingerprints and receipts. `StartConfig::find(home)` gives a computer's defaults: Claude Code's and Codex's folders (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, else in the home folder), the `claude`, `codex` and `agy` command lines, and that task folder.

Where a session lands is decided at each start, from what is installed:

- **Claude Code** runs as a background job (`claude --bg`). With Claude.app installed, the receipt says `handoffPending` and the job moves into the desktop app after its first turn (below).
- **Codex** with its desktop app, and always on Windows: a short-lived `codex app-server` creates and names the thread, the shared queue takes the first prompt, and `codex://threads/wake/<id>` opens it. Otherwise the shared daemon creates the thread and starts its first turn.
- **Antigravity**: the running language server starts a cascade and sends the prompt; with none running, `agy -p <prompt> --output-format json`.
- **Pi and OpenCode** start as a run of their command line with no window: `pi -p --session-id <request id>` and `opencode run`, in the folder and with `PWD` set to it (OpenCode 1.19 takes its folder from `PWD` first). The first prompt goes in on standard input, never as an argument, so nothing is quoted for a Windows `cmd.exe` shim and words starting with `@` are not read as a file to attach. The session is the client's own, saved where it keeps every other, so the client lists and resumes it. The start waits up to 20 seconds for it: Pi's `<time>_<id>.jsonl` under its sessions folder (named after the folder, `--<path with / \ : as ->--`), OpenCode's newest main session in that folder in `opencode.db`, made since the run began. The receipt then reads started with `pi:<id>` or `opencode:<id>`; a run that ended first is refused with the last line it printed; one still at work is uncertain. A run starts in the client's own model, so a named one is refused, and it asks nobody anything: `opencode run` turns down what would need an answer. Only the phone and the person's own window start them; `start_session` does not.

`Handoffs` follows each `handoffPending` receipt by session id and loads those still owed (up to 7 days old) at launch. Its owner asks right after the start and at regular looks; a host that sees the session's Stop hook can ask then too. A move goes ahead once the first turn stopped: the job's `state.json` reads `done`, `blocked` (the turn ended with a question) or `stopped` (an earlier move stopped it), or, for any state but `working`, the session's entry in Claude Code's `sessions/<pid>.json` registry reads idle. A registry entry at work (`busy`, `shell`, `waiting`) holds it, and so does a message still waiting to go into the session (`LocalClients::waits_for`), which goes first; the move then follows the next stop.

The move runs on its own thread: `claude stop <job>`, up to 10 seconds for the job's process to leave the registry, then `claude://resume?session=<id>`, and the receipt is saved with `handoffPending: false`. A failed move is tried at most three times in one run. A session another client holds (a registry `kind` other than `bg`, `daemon` or `daemon-worker`), a desktop app that is gone or a missing command line ends the move, with the reason on the receipt.

## Agent messages

Off until Settings → Agents → Agent tools → "Let agents message each other" is on (`agentMessages`, off by default). Under it, "Send as me" (`agentMessagesAsUser`, marked Caution) sends the words as the user's own, and "Passes in a row" (`agentMessagesLimit`: 1 to 1000, or null for no limit; 10 by default) caps a chain. Each client's own "Send messages" switch on its page still applies.

The MCP relay asks the app for the group's tools (`host_tools`) and lists `list_sessions`, `list_models`, `send_message`, `start_session` and `get_message` only while `agentMessages` is on; a call reaches the app as `host_tool`. The local tools channel listens while `hudTools` or `agentMessages` is on; HUD tools still answer only with `hudTools`. `AgentMessages` answers on the caller's thread against the app's latest snapshot, never with the application's lock held, so nothing is sent after the relay stopped waiting. Every 5 seconds, while a message still waits for something, it captures Claude Code and Harness deliveries before the plugins' files go and throws planes back.

- **Sender.** The relay names it, never an argument: Codex's `_meta.threadId` and turn, Antigravity's conversation id in `_meta`, Claude Code's `CLAUDE_CODE_SESSION_ID` in the relay's environment, and for Harness the session its plugin notes while the call runs. For Cursor, TRAE, WorkBuddy, ZCode, Qoder and Kimi Code, the session whose hooks ran from the process that started the relay (`hooks.pids` on the session), or, when none did, from the nearest process above it in the same application bundle: TRAE starts its hooks and its MCP servers from different helpers, which meet only at the app's own process, so a hook notes its nearest three processes and, when one of them lies in an app bundle, that app's processes above them. When several sessions match one process, the one of them in a turn; WorkBuddy and CodeBuddy note a turn from its prompt (`UserPromptSubmit`), so a session's first turn already counts. For Pi and OpenCode, the session whose observer, in the process that started the relay, noted a call of that tool (`calls/<pid>/`, written before the call runs and removed after): the note with the same arguments, else the only session calling it (`hooks::mailbox::caller`). A note or a hook names the sender before an inherited `CLAUDE_CODE_SESSION_ID`, which a client started from Claude Code carries. An id matches the snapshot's with or without the `antigravity:` or `deepseek:` prefix. No sender, no message.
- **Sessions.** `list_sessions` gives main sessions with client, title, project, state, the model the session last ran (`model`, from its log; null when unknown), `self`, and `reachable` with a reason: Claude Code and Harness are true when their plugin checked in and "Send messages" is on; Codex is false with neither a command line nor the shared daemon, true when an app has the thread open or can wake it, else null; Antigravity is null. `startFolders` says where each client can start.
- **Delivery.** Refused before anything is journaled: empty text, text starting with `[Agent HUD · iPhone]` (the user speaking from a phone), the caller's own session, a caller that is itself a sub-agent (it gives its result back in its own turn, to the session that started it; Open #111), an unknown or child session, another client, a steer to a client that takes none, or a session that cannot take it now. `send_message` is one `LocalClients::send` with `operation: enqueue` (or `steer`, below) and the message id (`m-` and 12 hex digits) as request id, noted as sent by `mcp:<client>`. It returns at once with the id, the state (`queued`, `uncertain`, or `refused` with the reason) and the pass. Agent HUD never cuts the text. Messages are never joined either: each is the recipient's own turn, so three partial messages about one task cost three turns that each read the task again (Open #54). The tool's description therefore asks the sender to finish thinking and send one whole message.
- **Steering** (Open #68). `delivery: steer` on `send_message` asks for the words to go into the recipient's turn in progress instead, so that turn reads a correction before it ends. The tool's description allows it only when the user explicitly asked for it; nothing can check that, so it rests on the sender following the description. Codex and DeepSeek Harness take one (`Provider::takes_steer`): the send is `operation: steer` naming no turn, which Codex's desktop owner or command line, or Harness's plugin, resolves to the turn in progress; `LocalClients::send` refuses a steer naming no turn for any other client. Claude Code's plugin cannot (`$.prompt.submit` runs once the session is idle), so a steer to any other client is refused before it is journaled. So is a steer that is a reply (`reply_to`: replies are always queued) and one to a session waiting on an approval or a question, which would read it only once that is answered. With no turn in progress the result is `refused` and nothing was sent; it is never queued instead, since a correction that comes after the turn may no longer be wanted. A steer that went in returns `steered`; its first line ends `· into your current turn`, and it always carries Agent HUD's label, even under "Send as me": another agent's words never read as the user's in the middle of a turn. It counts as a pass like any message, and since it begins no turn, a message the recipient sends in the turn it went into counts on from it (the turn's parent is the steer, matched by `steeredInto` against the caller's turn). The journal keeps the turn it went into (`steeredInto`), and `get_message` reads the answer from that turn, which began before the send. `list_sessions` gives `steerable` and `steerReason` from the snapshot: true for a running session, waiting on nothing, of a Codex whose thread an app has open or of a Harness whose plugin checked in.
- **Starts.** `start_session` takes `claude`, `codex`, `antigravity` or `deepseek` (and `startFolders` lists only these) and calls `SessionStarts::start_with` against offers worked out from every session in the snapshot. The folder defaults to the caller's project and must be offered; empty is the client's task folder. A Claude job bound for the desktop app is followed (`Follow`). A start counts as a pass, and a sub-agent cannot make one. Harness has no command that starts a session, so its plugin does it: each Harness host checks in under `hosts/<pid>.json` in `deepseek-channel`, the start is left for one host in `starts/<pid>/<request>.json` (the Desktop app's host first), and the plugin creates the session with `sessionController.create`, in the folder's Workspace when Harness has one, queues the first message and writes the session's id back. With no host running, the Desktop app is opened (`dsh://open`) and its host waited for. Harness is offered only while the plugin is installed and a host runs or the Desktop app is installed, and its start is refused while "Send messages" is off on the plugin's row. A product's own `SessionStarts` offers Harness only if it is given the channel (`with_deepseek_channel`).
- **Models.** A session runs its client's own choice unless a model is named, and the tool descriptions ask for one only when the user asked: the choice is the user's, so Agent HUD never picks a model and never changes one by itself. `list_models` (`client` optional; all four when left out) asks each client what it offers now (`SessionStarts::models`, `delivery::models`): `default` is the model a session gets with none named, which is the one the user last chose in that client, `atStart` and `perMessage` say whether `start_session` and `send_message` can name one, and each model has an `id`, the `name` its picker shows and, for Antigravity, `quota` (share left, `resetsAt`). A client whose list could not be read has `reason` instead.
  - Claude Code has no list to ask: its ids are the aliases `opus`, `sonnet` and `haiku` (`aliases: true`: any full model name is taken too, never a word starting with `-`), and its default is `model` in `~/.claude/settings.json`, else none (the account's). A start passes `--model`.
  - Codex: a short-lived app-server's `model/list`, the default from `config/read` (its settings), else the model it marks `isDefault`. A start through the shared CLI daemon names it in `thread/start` and the first `turn/start`. With the desktop app installed a start is refused with a model (`atStart: false`, `SessionStarts::model_at_start`): the app runs the new thread's queued first message in the model chosen in the app, and Codex keeps no model on a thread before its first turn (its `threads` row appears with that turn), so `thread/start` or `thread/settings/update` on the short-lived app-server do not carry over (checked 2026-11-17 on 0.162.1). A message cannot name one either: Codex's queue (`thread/queue/add`) carries input only.
  - Antigravity: `GetUserStatus`'s `clientModelConfigs` (disabled ones left out; proto JSON leaves a spent quota's `remainingFraction` out, read as 0). Its default is the picker's last choice, `last_selected_agent_model` in `~/.gemini/antigravity/antigravity_state.pbtxt` (one for all conversations, under `GEMINI_CLI_HOME` when set), else the status's default. Every message carries a model (`cascadeConfig`, the cascade's own configuration from its latest turn): the named one, else the picker's, else the one that turn used, else the status's default; without a model the service would choose its own. Only the last turns are read, never the whole conversation, which in a long session runs past the 16 MB a read may take: `GetConversationMetadata` gives the step count, and `GetTrajectoryTurns` with the last step's index gives that turn, whose first step is the user's input with its configuration; a turn whose input names no model leads to the one before, up to 20 turns back. Each answer is a few kilobytes and loads a conversation the service has not opened. A read that fails never stops the message: with no model named and no picker's choice it goes in the status's default, and its receipt's `reason` says so and why. An answer over the limit is worded with its size and the limit ("Antigravity's answer was 18.8 MB, over the 16 MB limit"), counted up to 64 MB and not kept. A start through the command line (no language server) takes no named model.
  - DeepSeek Harness: the plugin (channel version 2) writes `controller.modelCatalog()` into its host check-in every 10 minutes (`models`: `default` from `agentDefaultModel`, `groups` per provider), and ids are `provider/model`. A message or a start names it in its file (`model: {provider, model}`), and the plugin calls `selectModel` before the words go in. `selectModel` also saves the choice as Harness's default for new sessions, so the plugin puts the default it had back. A session or host whose plugin is older is refused with a model, asking for Harness to be restarted.
  - `model` on `send_message` is refused before anything is journaled for clients that cannot switch a running session (Claude Code, Codex and the hook clients), and on either tool when the client offers no model by that id or name (case aside), or its list cannot be read. A named model stays for the session's later turns, as if the user had picked it there.
- **Replies.** With `reply_to` naming a message the caller received, `to` may be left out: the reply goes to that message's sender. A reply that goes back to that sender and is not refused settles the message: the journal keeps the reply's id (never its words), `get_message` says `replied` with `reply` (or `done` once the turn's own answer reads, still naming `reply`), and the reply's plane is the only one back.
- **Form.** By default the recipient reads a first line `[Agent HUD · from <client> · <title> · <id>( · re <id>)]`, the text, and a last line in the app's language saying how to reply: with Agent HUD's `send_message` and `reply_to`, named as the recipient's client names it (`mcp__agent-hud__send_message` in Claude Code and Harness, `mcp__agent_hud__send_message` in Codex, "agent-hud's send_message tool" in Antigravity), since each client has a `send_message` of its own; a plain answer only without that tool. A reply's last line offers another reply only if more is needed, so two agents do not thank each other back and forth. A sender that passes `reply_hint: false` (on `send_message` or `start_session`) reads the answer itself with `get_message`: the last line then asks the recipient to answer in its turn and send nothing back. With "Send as me" the text goes alone (`PromptForm::Own`).
- **Passes.** Each message has a chain and a pass. When the caller's current turn began with one of Agent HUD's messages, its message continues that chain at the next pass; a turn the user began starts a new chain at pass 1. The caller's turn is its last prompt on its transcript's tail page (read from the start when the tail is refused, or shows no prompt but leaves earlier rows out); for Codex, the prompt of the turn `_meta` names. A message past the limit is refused until the user steps in. An unreadable transcript is no sign of the user: a reply continues the chain of the message it answers, anything else the newest chain the caller received.
- **Answers.** `get_message` gives `queued`, `taken`, `started`, `done` with `answer` (the last assistant text of the turn the message began), `replied`, `refused`, `expired` (not taken within the plugin's hour) or `uncertain`. It reads only what Agent HUD collected and never wakes the session: the recipient's `session_detail` pages, from where its transcript ended at the send. The message's row is found by its id in the label, or, sent as the user, by the SHA-256 of its words in a turn that began after the send. The turn has ended once a later turn shows (a turn Harness starts for a plugin's or background job's notice has no prompt, so any of its rows counts) or the session's `liveFacts` say so. Harness logs are compressed: the app pages their tail by decoding the whole log and refuses past 130 MiB of text, so such a log is read from its start; a forward page comes back `messagesPending` until the app's one decoder reaches it, 2 MiB a look, and one read asks again up to 70 times. A message Antigravity queued while a turn ran cannot be tied to its answer (its words are read as part of the running turn); only a reply through `send_message` comes back for it.
- **The plane.** Each pass flies a paper plane on every HUD (`Flight`, published as `hud:flight`; drawn by `src/packages/hud/src/scene/FlightLayer.tsx`) from the sender's mark to the recipient's. A message refused because its recipient cannot take it now, for the limit or on delivery falls halfway; for a start, the new session appears first and then catches it. Flights between the same two sessions share a lane: one in the air at a time, more riding along as a count. Around the notch, the chain's first sender stands on the left. The plane flies back once, when the recipient's live facts say a turn ended, the message's own turn is found and ended, and its answer reads. A turn that ended with nothing to read is given up a minute later without a plane; a turn not found yet is looked for until two hours after the send. A reply's own plain answer flies nothing: it reaches no one.
- **Journal.** `messaging/messages.json` in the host's data folder keeps a week of messages: who, to whom, chain, pass, form, fingerprint, state, where the turn was found and a reply's id. Never the words.

## The inspector

Experimental: its switches sit on Settings → Experimental (`src/packages/app/src/settings/ExperimentalPane.tsx`), and the bubble is off until the person switches it on (`clipboardBubble`; picks from the browser come up either way). The code calls its window the clipboard window (`inspect`, `clip…`). The person's own words from the HUD: what they copy goes into a Claude Code, Codex or DeepSeek Harness session, or a new one, as typed by them (`PromptForm::Own`, `Operation::Enqueue`), through the same senders. Host: `src/crates/host/src/inspect/`; sending: `Messaging::user_sessions` and `user_send` (`src/crates/messaging/src/user.rs`), which need only each client's own "Send messages" switch, not agent messages; HUD: `src/packages/hud/src/inspect/`.

- **The watch.** Every 400 ms the host reads the clipboard's change count; on a change, only the kinds of data the copy holds and the app in front (`inspect/clipboard/`, macOS only; Windows and Linux are stubs). A copy marked with the nspasteboard.org hidden types (password managers), one of Agent HUD's own, or any copy while "Show after each copy" is off empties the slot. The content is read when the window opens: reading the clipboard's content is what macOS may ask the person about.
- **One slot, one draft.** The latest copy holds one place that each copy takes over; it joins the draft only when the person adds it or writes a comment on it. With nothing added, a send carries the latest copy. The note goes first, then each item, numbered when there are several, under a line saying what it is and which app it came from; copied words sit in a code fence, a picture goes as the path of its PNG, kept a week in `~/.agenthud/tmp` (`clip-<id>.png`).
- **The bubble.** A third end of the dock, past the tail (or in its place while the tail is empty), with the tail's countdown ring: a copy's bubble goes after `clipboardFadeSeconds` (5 by default, 0 keeps it); with something in the draft it stays and counts it. The bubble and the tail count down alike (`ends/useEndFade.ts`): the pointer on one stops its clock and winds it back, so it has its whole time again once the pointer leaves. Any item, the latest copy too, can be let go with its ×.
- **The shortcut.** ⌥Z calls the window up again after its bubble has gone, with what it held, or with what is on the clipboard now (`inspect/shortcut.rs`; a Carbon hot key in `shell/macos_hotkey.rs`, none yet on Windows and Linux). Settings → Experimental has one field for it: clicked, it records the next combination (`clipboardShortcut`, saved as `Alt+KeyZ`: modifiers, then the key's `KeyboardEvent.code`; it must hold ⌘, ⌃ or ⌥), Delete clears it to none (saved empty), Esc or a click elsewhere keeps the old one; while it listens the host lets the old one go. The shortcut is held only while the bubble is on. The settings `clipboardBubble`, `clipboardFadeSeconds` and `clipboardShortcut` are global, kept with the display settings.
- **Marking up a picture.** A picture's thumbnail opens the markup window (`inspect/marking.rs`, label `inspect-mark`; page `src/packages/app/src/mark/`), on the screen under the pointer (`placement.rs`, as Settings and Statistics are), sized to the picture at one point per pixel within most of that screen, its toolbar in the title bar (`shell::toolbar_chrome`): a box, a circle, a pen and numbered comments (keys B, O, P, C; ⌘Z, ⌘↩ for Done, Esc to cancel). A comment is written beside its pin on an opaque card, so it reads on any picture; the list of every comment folds out at the right, folded away at first. Done draws the marks into the picture (a pin with no words goes, so the numbers match), saved beside it in `~/.agenthud/tmp`, which takes the picture's place in the draft; the comments go under it in the message as a numbered list. The host closes the window: its page has no right to. The HUD goes on as usual while the window is open; once it closes, however, the inspector comes up again (`presented`).
- **From the browser.** The extension (`src/apps/browser-extension/`) picks an element or an area and hands it over through Chrome's native messaging (`inspect/browser.rs`): the picture, the page, the selector, the words, the HTML and its styles. The HTML leaves out the marks a build adds to scope styles (Astro's `data-astro-cid-…`, Vue's `data-v-…`, Svelte's `svelte-…` classes), named once in the message instead; where a dev server marks elements with their place in the source (Astro's dev toolbar, vite-plugin-vue-inspector, code-inspector-plugin), that place leads the message as `Source:`.
- **Where it goes.** The place chosen last (`inspect/chosen.json`) while it is there; for a session that has gone, the newest session of the same client in the same folder; else the newest session that takes words. The list shows one client at a time, its sessions grouped by folder, each folder offering a new session there.

## Senders and stores

With Open alone, the host builds its own senders from the app's data folder: receipts in `local-client-receipts/` (starts in `local-client-receipts/starts/`), the Claude Code plugin's channel folder, the Harness plugin's `deepseek-channel/`, and `StartConfig::find` for the clients. It follows started Claude jobs into the desktop app itself, at the start and at each 5-second look.

A product build may hand over its own senders with `ProductExtension::delivery() -> Option<Delivery>`: its `LocalClients`, its `StartConfig`, where start receipts and the journal go, a `follow` for started Claude jobs, and optionally a store of conversation turns (`agent_hud_messaging::Turns`). Agent messages then share one sender owner with the product's own senders, so each session's messages keep their order. A store is read before transcript pages for Claude Code, Codex and Antigravity; Harness is always read from pages.
