# Agent messages and sending into sessions

Agent HUD can put words into a running Claude Code, Codex, Antigravity or DeepSeek Harness session, hand them to a Cursor, TRAE, WorkBuddy, ZCode, Qoder or Kimi Code session when one of its turns ends, or to an open Pi or OpenCode session once it is idle, and start a new Claude Code, Codex or Antigravity session. On top of that, agent messages let one agent session message, start and read another through Agent HUD's MCP server.

## Where the code lives

- `src/crates/platform/src/delivery/` (`agent_hud_platform::delivery`): sending into sessions (`LocalClients`, `Receipt`, `DeliveryState`), starting sessions (`SessionStarts`, `StartConfig`) and moving started Claude jobs into the desktop app (`Handoffs`). The `fixtures` cargo feature exposes `delivery::fixtures` to other crates' tests.
- `src/crates/messaging/` (crate `agent-hud-messaging`): the agent messages tool group (`Messaging`), its journal, the reading of answers and the paper plane (`Flight`).
- `src/crates/host/src/messages.rs` (`AgentMessages`): the host's owner of the group.
- Settings: `src/packages/app/src/settings/agent-plugins/AgentMessagesRow.tsx` and the "Send messages" switches in `KnownClientCard.tsx`. The relay's side is in [the MCP app](../src/apps/mcp/README.md).

## Sending into a session

`LocalClients` is one synchronous owner per app; share its `Arc` rather than making a second one. A gate per session keeps that session's sends in order without holding up other sessions. Its calls block, so a GUI host runs them off the UI thread. The host hands it the main sessions it already knows (`update_targets`). Making one scans no transcript, installs nothing, changes no client setting and launches no app.

- **Request ids** are the caller's and stay the same for one attempt (letters, digits, `-` and `_`, at most 128 bytes); the client sees `agent-hud:<id>`.
- **Journal.** Before anything is sent, a file in the receipts folder records a SHA-256 fingerprint of the request and an `uncertain` receipt, never the words. The same id again returns that attempt; the same id with other words or options fails.
- **No blind retries.** Once bytes may have left, a timeout, a disconnect, an unreadable acknowledgement or a crash leaves the receipt `uncertain`. Nothing is sent again, through the same owner or another.
- **Receipts** keep the session and thread ids, both request ids, and the turn and Desktop owner when known; `known_receipts` gives the last 7 days. `delivered` and `started` note which of Agent HUD's surfaces sent a prompt, so the session's tags name the sender and not the app that took it.

### Claude Code

Through Agent HUD's Claude Code plugin (`src/crates/platform/src/claude_plugin`), installed from Settings → Agent plugins. Every session running it checks in to the folder it shares with the app every 5 seconds; a check-in counts for 20 seconds. A send is left in that folder, and the plugin claims it before calling `$.prompt.submit`. The words wait for the session to go idle while check-ins go on, and the receipt reads taken, started or refused.

- Only automatic and enqueue sends; slash commands are refused. Words nobody claimed within an hour expire.
- Cancelling is a request until the plugin acknowledges it; words already taken cannot be promised withdrawn.
- `maintain` captures the plugin's last states before it removes taken files a minute later. It is housekeeping, not a collector.
- "Send messages" on the plugin's row (`claudeMessages`, on by default) decides whether any message from Agent HUD goes into a Claude Code session. Senders check it and refuse with `delivery::CLAUDE_MESSAGES_OFF`.

### Codex

- **Desktop owner first.** Automatic, start, steer and interrupt sends go to the Codex desktop app that owns the thread. Only a proven absence of that owner, before anything is written, lets a send try the command line: a thread loaded in a live TUI, reached through Codex's shared daemon. It never runs `codex -p`, resumes the thread in another engine or opens a second TUI.
- An automatic send reads the thread's running state and makes one start or steer. A steer names the turn it expects, and a command-line interrupt names the exact turn. The desktop owner has no interrupt, and accepted input cannot be withdrawn.
- **Enqueue** (what agent messages use) puts the words into Codex's shared queue (`thread/queue/add`) without loading the thread: through the shared daemon when one runs, else through a short-lived `codex app-server` started from the host's `QueueRoute` (`StartConfig::codex_queue`). Whichever app has the thread open sends the item as a new turn once the thread is idle, so it never steers or interrupts. The receipt is `queued` with no turn; the turn is found later by its `agent-hud:<id>`.
- An app holds `thread-writer-locks/<thread>.lock` in Codex's folder while it has the thread loaded (`codex_thread_open` asks without waiting). When no app holds it and Codex's desktop app (Codex.app or ChatGPT.app) is installed, the host opens `codex://threads/wake/<thread>`; otherwise the item waits until a Codex opens the thread.
- Desktop apps are looked for only on macOS (`/Applications`, `~/Applications`). On Windows, Codex takes desktop start, steer and automatic sends and the queue (through the short-lived app-server), without command-line owner control or interrupt.

### Antigravity

Through the running Antigravity local language server: enqueue delivers when the session is idle, steer at the next invocation, and interrupt cancels the cascade. Whether the server is there is found out at submission, so `reachable` stays null until then. The route is verified on macOS and unverified on Linux; on Windows it sends into existing sessions but cannot interrupt or start one.

### DeepSeek Harness

Through Agent HUD's DeepSeek Harness plugin (`src/crates/platform/src/deepseek_plugin`), with the Claude Code plugin's protocol over `deepseek-channel` in the app's data folder (`LocalClients::with_deepseek_channel`; without it no Harness session takes a message). A session that checked in within 20 seconds takes automatic and enqueue sends; slash commands are refused. The plugin hands each prompt to Harness's session controller with `mode: 'queue'`, so it joins the session's own queue and never interrupts a turn; the file then says taken, started (Harness queued it) or refused.

The snapshot names a Harness session `deepseek:session-<uuid>`; Harness, its plugin and the relay's caller name it `session-<uuid>`. Both are taken. "Send messages" on the plugin's row (`deepseekMessages`, on by default) decides whether any message goes into a Harness session (`delivery::DEEPSEEK_MESSAGES_OFF`). Agent HUD does not start Harness sessions.

### Cursor, TRAE, WorkBuddy, ZCode, Qoder and Kimi Code

Through the session's own completion hook, the only route these clients support, and in Qoder CLI also its rewake hook (`docs/client-hooks.md`). A send is left in the `hook-channel` folder of the receipts folder under `<client>--<session>`; when the session's `Stop` (Cursor: `stop`) hook fires, it claims the oldest message and replies with it in the client's own continuation form, so the client takes it as the next input and carries the turn on. The receipt reads waiting until then, started after. A message a session has not taken within an hour expires.

- Only automatic and enqueue sends; slash commands are refused, and so is a ZCode message over 24,000 characters (ZCode cuts hook text there).
- A turn is carried on only as often as the client allows; the rest wait for a later stop. WorkBuddy and CodeBuddy set no cap and Agent HUD adds none, so there only the limit on passes between agents ends a chain.
- An idle session takes nothing until its next turn ends, except in Qoder CLI: there Agent HUD's rewake hook waits in an interactive session from its start and from each turn's end, and hands a message over at once, so the idle session answers it (`docs/client-hooks.md`). `list_sessions` says which: reachable `true` while a turn runs or a rewake hook waits, `null` for another idle session, and `false` until its client's hooks have reported to Agent HUD (`hooks.at` on the session, for this session or another of the same client in the last week). TRAE runs hooks only once its global hooks are on (TRAE Settings → Hooks).
- Their agents send with Agent HUD's MCP server in each client's own settings file. WorkBuddy starts a server from `~/.workbuddy/mcp.json` only after the user trusts it once (Connectors → Custom connectors); TRAE splits a server's `command` at its spaces unless it is in double quotes, so Agent HUD writes its path quoted there.
- The follow-up the hook notes names the message it handed over (`delivered`), which is how `get_message` finds its turn when the client keeps no readable log (TRAE, Cursor): the answer is the reply the next completion reports, its first 40 KB. Cursor's `stop` carries no reply, so it is read from the end of the transcript the hook names: the last assistant text after the turn's prompt, never an older turn's.
- Agent HUD sees only a session's latest turn of these clients, so the answer read when its plane is thrown back is kept in memory, never in the message log (`answers.rs`, the newest 64): `get_message` still gives it after the session's next turn ends, until Agent HUD restarts. Live facts that name the message as the turn that ended count even while the session's next turn runs.

### Pi and OpenCode

Through Agent HUD's own observer in the client: Pi's extension and OpenCode 1's plugin (`docs/client-hooks.md`) carry a mailbox (`src/crates/agents/src/hooks/mailbox.js`), with the path of the app's `hook-channel` written in when Agent HUD installs them (`Clients::with_channel`; Oh My Pi, Kilo Code, MiMo Code and OpenCode 2 get none). A send waits under `prompts/<client>--<session>` as for the hook clients above, and the observer claims it the same way (`ClaudeChannel::take_next`).

- An open session takes a message once it is idle: Pi when its run settles (`agent_settled`) or within two seconds, as `pi.sendUserMessage`; OpenCode within two seconds, as `session.promptAsync` with the model and agent of the session's newest prompt, as OpenCode itself resumes a session (without them OpenCode runs it on the agent's default model). A message that comes while a turn runs waits for its end.
- While its process runs, each observer says which sessions it holds (`observers/<client>@<pid>-<instance>.json`, every 20 seconds in Pi, every 30 in OpenCode, which lists its server's main sessions). `list_sessions` says reachable `true` for a session an observer named in the last 75 seconds from a process that still runs, `null` otherwise (`hooks::mailbox::standing`). An observer removes the file of a process that is gone.
- The turn's record names the message (`delivered`) and carries the reply's text, its first 40,000 characters, which `get_message` returns; a turn that took a message and failed or was stopped is recorded as ended, so its message is done without an answer. As for the hook clients above, the answer is kept in memory once read.
- Only automatic and enqueue sends; slash commands are refused. Pi and OpenCode read Agent HUD's MCP server from `~/.pi/agent/mcp.json` and the `mcp` key of `~/.config/opencode/opencode.json`, and its skill from `~/.agents/skills` (OpenCode also reads `~/.claude/skills`, so a second copy there is a duplicate it warns of).

## Starting sessions

`SessionStarts` starts a session with a first prompt, which cannot begin with `/`, in a folder offered from existing sessions (`offers_for`: per client, the ten latest project folders that still exist and that its workspace trust accepts) or with no project in `~/.agenthud/sessions/<client>/<request>`, whose Claude Code folder is marked trusted in Claude Code's settings first. A client is offered when its command line is found (Antigravity also when its desktop app is installed). Starts have their own request ids, fingerprints and receipts. `StartConfig::find(home)` gives a computer's defaults: Claude Code's and Codex's folders (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, else in the home folder), the `claude`, `codex` and `agy` command lines, and that task folder.

Where a session lands is decided at each start, from what is installed:

- **Claude Code** runs as a background job (`claude --bg`). With Claude.app installed, the receipt says `handoffPending` and the job moves into the desktop app after its first turn (below).
- **Codex** with its desktop app, and always on Windows: a short-lived `codex app-server` creates and names the thread, the shared queue takes the first prompt, and `codex://threads/wake/<id>` opens it. Otherwise the shared daemon creates the thread and starts its first turn.
- **Antigravity**: the running language server starts a cascade and sends the prompt; with none running, `agy -p <prompt> --output-format json`.

`Handoffs` follows each `handoffPending` receipt by session id and loads those still owed (up to 7 days old) at launch. Its owner asks right after the start and at regular looks; a host that sees the session's Stop hook can ask then too. A move goes ahead once the first turn stopped: the job's `state.json` reads `done`, `blocked` (the turn ended with a question) or `stopped` (an earlier move stopped it), or, for any state but `working`, the session's entry in Claude Code's `sessions/<pid>.json` registry reads idle. A registry entry at work (`busy`, `shell`, `waiting`) holds it, and so does a message still waiting to go into the session (`LocalClients::waits_for`), which goes first; the move then follows the next stop.

The move runs on its own thread: `claude stop <job>`, up to 10 seconds for the job's process to leave the registry, then `claude://resume?session=<id>`, and the receipt is saved with `handoffPending: false`. A failed move is tried at most three times in one run. A session another client holds (a registry `kind` other than `bg`, `daemon` or `daemon-worker`), a desktop app that is gone or a missing command line ends the move, with the reason on the receipt.

## Agent messages

Off until Settings → Agent plugins → Agent tools → "Let agents message each other" is on (`agentMessages`, off by default). Under it, "Send as me" (`agentMessagesAsUser`, marked Caution) sends the words as the user's own, and "Passes in a row" (`agentMessagesLimit`: 1 to 1000, or null for no limit; 10 by default) caps a chain. The plugin rows' "Send messages" switches still apply.

The MCP relay asks the app for the group's tools (`host_tools`) and lists `list_sessions`, `send_message`, `start_session` and `get_message` only while `agentMessages` is on; a call reaches the app as `host_tool`. The local tools channel listens while `hudTools` or `agentMessages` is on; HUD tools still answer only with `hudTools`. `AgentMessages` answers on the caller's thread against the app's latest snapshot, never with the application's lock held, so nothing is sent after the relay stopped waiting. Every 5 seconds, while a message still waits for something, it captures Claude Code and Harness deliveries before the plugins' files go and throws planes back.

- **Sender.** The relay names it, never an argument: Codex's `_meta.threadId` and turn, Antigravity's conversation id in `_meta`, Claude Code's `CLAUDE_CODE_SESSION_ID` in the relay's environment, and for Harness the session its plugin notes while the call runs. For Cursor, TRAE, WorkBuddy, ZCode, Qoder and Kimi Code, the session whose hooks ran from the process that started the relay (`hooks.pids` on the session), or, when none did, from the nearest process above it in the same application bundle: TRAE starts its hooks and its MCP servers from different helpers, which meet only at the app's own process, so a hook notes its nearest three processes and, when one of them lies in an app bundle, that app's processes above them. When several sessions match one process, the one of them in a turn; WorkBuddy and CodeBuddy note a turn from its prompt (`UserPromptSubmit`), so a session's first turn already counts. For Pi and OpenCode, the session whose observer, in the process that started the relay, noted a call of that tool (`calls/<pid>/`, written before the call runs and removed after): the note with the same arguments, else the only session calling it (`hooks::mailbox::caller`). A note or a hook names the sender before an inherited `CLAUDE_CODE_SESSION_ID`, which a client started from Claude Code carries. An id matches the snapshot's with or without the `antigravity:` or `deepseek:` prefix. No sender, no message.
- **Sessions.** `list_sessions` gives main sessions with client, title, project, state, `self`, and `reachable` with a reason: Claude Code and Harness are true when their plugin checked in and "Send messages" is on; Codex is false with neither a command line nor the shared daemon, true when an app has the thread open or can wake it, else null; Antigravity is null. `startFolders` says where each client can start.
- **Delivery.** Refused before anything is journaled: empty text, text starting with `[Agent HUD · iPhone]` (the user speaking from a phone), the caller's own session, an unknown or child session, another client, or a session that cannot take it now. `send_message` is one `LocalClients::send` with `operation: enqueue` and the message id (`m-` and 12 hex digits) as request id, noted as sent by `mcp:<client>`. It returns at once with the id, the state (`queued`, `uncertain`, or `refused` with the reason) and the pass. Agent HUD never cuts the text. Messages are never joined either: each is the recipient's own turn, so three partial messages about one task cost three turns that each read the task again (Open #54). The tool's description therefore asks the sender to finish thinking and send one whole message.
- **Starts.** `start_session` takes `claude`, `codex` or `antigravity` and calls `SessionStarts::start_with` against offers worked out from every session in the snapshot. The folder defaults to the caller's project and must be offered; empty is the client's task folder. A Claude job bound for the desktop app is followed (`Follow`). A start counts as a pass. A Harness start is refused, saying `send_message` reaches an open one.
- **Replies.** With `reply_to` naming a message the caller received, `to` may be left out: the reply goes to that message's sender. A reply that goes back to that sender and is not refused settles the message: the journal keeps the reply's id (never its words), `get_message` says `replied` with `reply` (or `done` once the turn's own answer reads, still naming `reply`), and the reply's plane is the only one back.
- **Form.** By default the recipient reads a first line `[Agent HUD · from <client> · <title> · <id>( · re <id>)]`, the text, and a last line in the app's language saying how to reply: with Agent HUD's `send_message` and `reply_to`, named as the recipient's client names it (`mcp__agent-hud__send_message` in Claude Code and Harness, `mcp__agent_hud__send_message` in Codex, "agent-hud's send_message tool" in Antigravity), since each client has a `send_message` of its own; a plain answer only without that tool. A reply's last line offers another reply only if more is needed, so two agents do not thank each other back and forth. With "Send as me" the text goes alone (`PromptForm::Own`).
- **Passes.** Each message has a chain and a pass. When the caller's current turn began with one of Agent HUD's messages, its message continues that chain at the next pass; a turn the user began starts a new chain at pass 1. The caller's turn is its last prompt on its transcript's tail page (read from the start when the tail is refused, or shows no prompt but leaves earlier rows out); for Codex, the prompt of the turn `_meta` names. A message past the limit is refused until the user steps in. An unreadable transcript is no sign of the user: a reply continues the chain of the message it answers, anything else the newest chain the caller received.
- **Answers.** `get_message` gives `queued`, `taken`, `started`, `done` with `answer` (the last assistant text of the turn the message began), `replied`, `refused`, `expired` (not taken within the plugin's hour) or `uncertain`. It reads only what Agent HUD collected and never wakes the session: the recipient's `session_detail` pages, from where its transcript ended at the send. The message's row is found by its id in the label, or, sent as the user, by the SHA-256 of its words in a turn that began after the send. The turn has ended once a later turn shows (a turn Harness starts for a plugin's or background job's notice has no prompt, so any of its rows counts) or the session's `liveFacts` say so. Harness logs are compressed: the app pages their tail by decoding the whole log and refuses past 130 MiB of text, so such a log is read from its start; a forward page comes back `messagesPending` until the app's one decoder reaches it, 2 MiB a look, and one read asks again up to 70 times. A message Antigravity queued while a turn ran cannot be tied to its answer (its words are read as part of the running turn); only a reply through `send_message` comes back for it.
- **The plane.** Each pass flies a paper plane on every HUD (`Flight`, published as `hud:flight`; drawn by `src/packages/hud/src/scene/FlightLayer.tsx`) from the sender's mark to the recipient's. A message refused because its recipient cannot take it now, for the limit or on delivery falls halfway; for a start, the new session appears first and then catches it. Flights between the same two sessions share a lane: one in the air at a time, more riding along as a count. Around the notch, the chain's first sender stands on the left. The plane flies back once, when the recipient's live facts say a turn ended, the message's own turn is found and ended, and its answer reads. A turn that ended with nothing to read is given up a minute later without a plane; a turn not found yet is looked for until two hours after the send. A reply's own plain answer flies nothing: it reaches no one.
- **Journal.** `messaging/messages.json` in the host's data folder keeps a week of messages: who, to whom, chain, pass, form, fingerprint, state, where the turn was found and a reply's id. Never the words.

## Senders and stores

With Open alone, the host builds its own senders from the app's data folder: receipts in `local-client-receipts/` (starts in `local-client-receipts/starts/`), the Claude Code plugin's channel folder, the Harness plugin's `deepseek-channel/`, and `StartConfig::find` for the clients. It follows started Claude jobs into the desktop app itself, at the start and at each 5-second look.

A product build may hand over its own senders with `ProductExtension::delivery() -> Option<Delivery>`: its `LocalClients`, its `StartConfig`, where start receipts and the journal go, a `follow` for started Claude jobs, and optionally a store of conversation turns (`agent_hud_messaging::Turns`). Agent messages then share one sender owner with the product's own senders, so each session's messages keep their order. A store is read before transcript pages for Claude Code, Codex and Antigravity; Harness is always read from pages.
