# Client hooks and requests

The public Swift implementation (`Sources/AgentHUDCore/Hooks` in `agent-hud-native-open`) remains the behavioral reference. This port separates pure client formats, shared request ownership, OS transport, and UI. It does not install itself from a preview bundle.

## Ownership

| Layer | Location | Responsibility |
| --- | --- | --- |
| Client formats | `src/crates/agents` | Per-client event/configuration parsing and response encoding. No filesystem, process, socket, credential, or desktop send operation. |
| Shared requests | `src/crates/core/src/requests.rs` | One ephemeral queue, connection cancellation, changed timeouts, dismissal until native settlement, exact Codex turn reviewer evidence, and native response receipts. |
| Session presentation | `src/crates/core/src/hook_events.rs`, `presentation.rs` | Overlay source-reported attention, origins, compaction, completion, and pending requests on fresh session views. Native waiting flags affect phase without fabricating an actionable card or activity clock. No token ledger mutation. |
| Platform IO | `src/crates/platform/src/hooks` | Unix callbacks, pending-only Claude transcript withdrawal, origin ancestry, offline event inbox, reviewed configuration changes, and Codex Desktop approvals/questions. |
| Application | `src/crates/runtime`, desktop `Service` | One runtime, immediate request notifications, existing transcript collection cadence, and independent transport stop/configuration outside the collector lock. |
| UI | `src/packages/hud/src/RequestActions.tsx` | Permission decisions, exact question keys/choices/custom text and skipped questions, plan approval/accept edits/feedback, leave-to-client, and errors. shadcn source is unchanged. |

HUD text fields acquire temporary native keyboard focus only on an explicit text-control click, and release it on withdrawal, blur or unmount. On macOS the HUD is a nonactivating `NSPanel` (see `docs/tao-panel-patch.md`): the click makes it key without activating this app, so the frontmost application stays active, and releasing the lease hands keys back to that application. Other platforms focus a normal Tauri window. This keyboard handoff has not been verified in a live GUI.

The UI's acknowledgment means the local request owner accepted the decision. Native response receipts distinguish confirmed, failed, and uncertain delivery. A missing native acknowledgment never causes an automatic resend. Receipts are bounded and ephemeral; request bodies are not stored as history.

## Current adapters

- Completion callback formats: Antigravity, Cursor, Copilot, CodeBuddy, WorkBuddy, Qoder, Qoder CN, QoderWork, ZCode, Qwen Code, Devin, Hermes, Factory Droid, Goose, TRAE, TRAE CN and Kimi Code.
- Messages from other agents (`docs/agent-messages.md`) go into a Cursor, TRAE, WorkBuddy, ZCode, Qoder or Kimi Code session only through that session's own completion hook, when one of its turns ends: the hook's reply carries the message on as the next input, in the form each client documents (Cursor `followup_message`; TRAE, ZCode and WorkBuddy `decision: "block"` with the text as `reason`; Qoder `decision: "deny"` with a reason; Kimi a denied `permissionDecision` with the text as its reason). A turn is carried on at most as often as the client allows (Cursor 4 of its default 5, TRAE 4, ZCode 3, Kimi 1, WorkBuddy and Qoder 3), counted from Cursor's `loop_count`, else `stop_hook_active` and Agent HUD's own chain in `hook-channel/chains`; a message past that waits for the next stop. Only Qoder CLI (Qoder and Qoder CN) documents a way to start a turn in an idle session, and Agent HUD uses it (below); nothing else is done to reach an idle session of any of them: no app bundle, binary, database, extension or security setting of theirs is touched, and no `-p` run is started.
- Qoder CLI's rewake hook (`--rewake-hook`, `Hooks::rewake`): a `SessionStart` and a `Stop` handler with `asyncRewake: true` and a 24-hour timeout. Qoder runs such a hook in the background and, when it exits with 2, queues what it wrote to stderr as the session's next message, which an idle session answers at once (docs.qoder.com/cli/hooks; seen with Qoder CLI 1.1.86). The hook waits for a message queued for its session, claims it and exits so; one waiter stands per session (`hook-channel/waiters/<key>/<pid>.json`), the newest, and it leaves when its Qoder quits (Qoder leaves such hooks running) or moves to another session (`/clear`). Qoder runs asyncRewake hooks in the background only while it is interactive; with `-p`, `--prompt` or `--print`, in CI, or when its stdin or stdout is no terminal it would wait for the hook to end, so there the hook leaves at once. Each queued message is claimed once (a `<id>.claim` beside it), whichever of this hook and the `Stop` completion hook comes first. QoderWork's desktop app is not given it.
- These hooks also note the processes they ran from (`pids`, up to three parents; `hooks.pids` on the session), which names the session behind an MCP call from the same client (`host::tools::hook_caller`).
- Permission callback formats: Claude Code, Codex, Qoder, Qoder CN, QoderWork, CodeBuddy, WorkBuddy, ZCode, Qwen Code, Devin, Copilot CLI (once the user turns it on, below), and Factory Droid. Each retains its own capabilities; an unsupported question/plan stays in the original client.
- Hermes: shell hooks in its `config.yaml` (`hooks:`, one list of `{command, timeout}` handlers per event), edited as text so only Agent HUD's own handler lines change; a layout the editor cannot follow (flow style, quoted keys) is refused, and every edit must read back as the old file plus Agent HUD's handlers. A turn runs from `pre_llm_call`, stays running at each `pre_tool_call`, waits from `pre_approval_request` (unless Hermes's auxiliary model decides it) to `post_approval_response`, and ends at `on_session_end`, which Hermes fires after every turn. Every profile is a Hermes home of its own (`~/.hermes/profiles/<name>/`, chosen by `-p`, the profile's alias or `hermes profile use`) that reads its own `config.yaml` and keeps its own approvals, so the handlers go into the default profile's file and every profile's that has a `config.yaml`, and come out of each; a profile without one is left alone, and a file that cannot be changed fails alone. Session ids are the ones `state.db` holds, with a profile's name in front as the usage reader writes them: the profile is the payload's `profile` (newer Hermes) or else the one whose folder is the hook's `HERMES_HOME`, since Hermes 0.19's payloads do not name it (`Hooks::environment`). A 0.19 gateway that serves several profiles from one process runs them all under one `HERMES_HOME`, so their events read as that home's. Hermes asks once for each of the five `(event, command)` pairs in each profile, the next time `hermes chat` starts in it; its gateway never asks and runs them only once approved. Running and waiting lapse after two minutes without a newer event, as for Cursor. Hermes's `pre_approval_request` only observes, so approvals stay in Hermes.
- Kimi Code (`config.toml`, `[[hooks]]` tables of `event`, `command` and `timeout` in seconds; `KIMI_CODE_HOME`, else `~/.kimi-code`): a `UserPromptSubmit` and a `Stop` handler, put in and taken out with `toml_edit` so every other table, key and comment stays as written. They exist to hand a session the messages other agents send it (above); the session's state still comes from its log, which records every turn's start and end and each approval or question (`interaction.request` until `interaction.resolved`) the moment they happen. Kimi runs `Stop` only while the turn has not been carried on yet, once per turn. No request is answered from the HUD: Kimi's `PermissionRequest` hook only observes and its deny-only `PreToolUse` would hold every tool call. The Kimi desktop app runs its own copy of Kimi Code from its Application Support folder and rewrites that copy's `config.toml` at every start; it is not covered.
- Copilot CLI's `permissionRequest` (in `~/.copilot/hooks/agent-hud.json`, beside `agentStop`) names `sessionId`, `toolName` and `toolInput`, and takes only `{"behavior":"allow"|"deny"}`: no standing rule, question or plan. With no decision the hook exits 0 and writes nothing, so Copilot asks in its own prompt, as it does after a timeout (fail-open). Copilot asks this hook before its own rules and session approvals, so a run with `-p`, `--allow-all-tools`, `--allow-all` or `--yolo` is left to Copilot. `preToolUse` is not used: Copilot denies a tool call when that hook fails. Because Copilot asks this hook first, an interactive session waits on the HUD for every call it would otherwise allow by itself, so the hook is installed only once the user turns it on (`Permission::opt_in`): the switch on Copilot's page in Settings → Agents adds `copilot` to the `optInApprovals` setting, a list of the clients whose opt-in hook is on. While client hooks are on, turning it on puts `permissionRequest` in and turning it off takes it out, `agentStop` staying; with client hooks off it waits for them. Turning client hooks off takes it out with the others.
- Goose finds Agent HUD's hooks as a plugin of its own, `~/.agents/plugins/agent-hud/hooks/hooks.json`, and turns it on by itself. Its `UserPromptSubmit`, `PostToolUse` and `PostToolUseFailure` say a turn is running, its `Stop` that it ended (answered `{"decision":"allow"}`, so Goose never reads the answer as a failed hook). Only Goose's own payloads count: they carry `event` and `matcher_context`, which other clients reading the same folder do not send. There is no permission hook: `PreToolUse` runs after Goose's own approval, or with none in its default auto mode, so answering it would add a second question rather than answer Goose's. Since Goose turns the plugin on without asking, the hooks are not installed until they are checked against a running Goose (no OS has a launch yet); Goose's sessions and tokens still come from its database.
- Cline's hooks can only cancel a step, so none are installed for Cline or Roo Code; their sessions come from their files alone.
- TRAE and TRAE CN (`~/.trae/hooks.json`, `~/.trae-cn/hooks.json`, groups under `hooks.<Event>` beside `"version": 1`): `UserPromptSubmit` and `PostToolUse` say the session is running (the prompt titles it), `Stop` ends the turn, and a `Notification` of type `permission_prompt` says it waits (until the next hook, up to 30 minutes). They are the only source of its sessions: TRAE keeps its conversations encrypted with a key only the running app holds, and reports no model or tokens, so its sessions show no usage. No request is answered from the HUD: a hook's `allow` does not lift a tool TRAE asks about by itself, so approvals stay in TRAE's window. TRAE runs the hooks only after the user turns on its global hooks (TRAE Settings → Hooks); the agent's settings page and the hook details say so. In TRAE's sandbox mode the user's folders are read-only to a hook, so a callback that cannot write the inbox hands its event to the running app over the hook channel, which keeps it (`handed_event`); with the app closed such events are lost.
- A client that imports another client's hooks: TRAE and Devin run Claude Code's hooks from `~/.claude/settings.json` too, with their own payloads and `CLAUDE_PROJECT_DIR` set. Such a callback records nothing and answers nothing, so it never becomes a Claude Code session, and the client's own hooks are the ones that count (`agents::process::IMPORTERS`; each rule sees the callback's caller and payload). TRAE's: no `transcript_path` and TRAE's signs (`TRAE_PROJECT_DIR`, `workspace_roots`; `trae/process.rs`). Devin's (`devin/process.rs`): the process running the callback, past any shell, is the `devin` program; or, with no process to go by, `DEVIN_PROJECT_DIR` and no `transcript_path`. Claude Code names its transcript in every callback and runs its own hooks, so Claude Code in TRAE's or Devin Desktop's terminal, or started by Devin's agent from its shell tool, stays Claude Code's.
- Claude attention, automatic compaction, and verified Claude/Codex/Devin session origin. An origin never establishes a running turn; attention never reopens a terminal turn. Compaction expires after five minutes or a newer source record.
- Claude Code session endpoint: the origin hook records the host of `ANTHROPIC_BASE_URL` (no path, query or key) and which cloud platform switch is on, as the session's environment holds them, so its calls are recorded under their route (a relay, a cloud platform, a local server) and priced accordingly. At `SessionStart` a host on this computer or its local network is asked over HTTP what serves it (Ollama, LM Studio, llama.cpp, vLLM) and with which context window; nothing else is contacted. The endpoint is kept per session in `ingestion.sqlite` and never synced.
- Devin Desktop's local agent, Devin Local, is the Devin CLI the app bundles, run over ACP (`devin acp`). It reads the same `~/.config/devin/config.json` hooks as the CLI, so one set of Devin hooks covers both. The origin hook (`SessionStart`, `UserPromptSubmit`) tells them apart by the caller: `devin acp` under the Devin Desktop app (bundle `com.exafunction.windsurf`) is Devin Desktop; `devin` in a terminal, or a `devin acp` the CLI's own `--cloud` REPL started, is Devin CLI; `devin acp` under another app is that editor's (`ide:zed`). The session's `client` then reads "Devin Desktop" or "Devin CLI"; for an editor, or with hooks off, it stays "Devin". Devin Desktop is Windsurf renamed in place (its `product.json` names it `Devin`, `oldNameShort` `Windsurf`), so its bundle is tagged `devin`: a session started in its terminal is `cli:devin`. Devin runs each hook as `bash -c`, `bash` from the `PATH`, so a shell between Devin and the hook is passed over. Devin also imports Claude Code's hooks by default (Devin's `read_config_from.claude`) and runs them beside its own; those callbacks are left out (above). Cascade, the desktop app's older agent, runs its own hooks from the Windsurf folder (`hooks.json`); those are not followed. Facts from Devin CLI 3000.11.234's bundled docs and binary and Devin Desktop 3.11.238's files; not yet exercised with an installed Devin.
- Codex permissions require the exact turn to explicitly have `approvals_reviewer: "user"`. Unknown, absent, or automatic reviewers remain with the client. A permission policy is not proof of a human reviewer.
- Codex Desktop app/browser approvals and asynchronous questions use the existing owner's local stream. This observer does not create a second conversation engine.
- Session observers: Pi's extension reports each turn's state and OpenCode's plugin each completed turn. OpenCode 1 and OpenCode 2 load the same script (`plugin/agent-hud.js`): it exports OpenCode 2's plugin when OpenCode 2 provides `@opencode/plugin`, and OpenCode 1's plugin function otherwise. Under OpenCode 2 it reads the finished reply when an execution succeeds, and its records name no terminal, since OpenCode 2 runs plugins in its background service. Their forks load the same scripts, written for their own folders and ids: Oh My Pi's extension (`~/.omp/agent/extensions/agent-hud.ts`), which settles a run when `agent_end` says it will not continue, since Oh My Pi has no `agent_settled`; and Kilo Code's and MiMo Code's plugins (`plugins/agent-hud.js` in `$XDG_CONFIG_HOME/kilo` and `$XDG_CONFIG_HOME/mimocode`). They report state only: no approvals. Pi's extension and OpenCode 1's plugin also hand their sessions other agents' messages and note calls of Agent HUD's MCP tools (`docs/agent-messages.md`). MiMo Code's desktop app loads no plugins of the user's, so its sessions show tokens without live state.
- Factory Droid's hooks live in `~/.factory/hooks.json`, keyed by event at the top level. Droid also runs the `hooks` of `~/.factory/settings.json`, event by event, for every event `hooks.json` leaves out, so installing one of Agent HUD's hooks first copies that event's groups from `settings.json` into `hooks.json` (as Droid's own `/hooks` does when it saves); `settings.json` is only read. Droid has no permission event: `PreToolUse` runs before every call its matcher names (`Create|Edit|ApplyPatch|Execute|WebSearch|FetchUrl`), and only a call Droid would ask about is held. Before a command goes to the HUD the hook reads the user's own command rules (`Permission::policy`, `droid/rules.rs`): `permissionRules` (`allow`, `ask` or `block`, matched by `match.prefix`) and the deprecated `commandAllowlist`, `commandDenylist` (ask, not refuse) and `commandBlocklist`, from `settings.json` with `settings.local.json` merged on top, both in the Factory folder (`$FACTORY_HOME_OVERRIDE/.factory`, else `~/.factory`) and in the session folder's `.factory`. A block comes before an ask, an ask before an allow. A command a rule allows or blocks is left to Droid with no answer, so the HUD never allows a command Droid may refuse; one an `ask` rule or the denylist names is held at every level, High included. Everything else is held by the session's autonomy level: a file change or web call at Off, a command whose `riskLevel` is above the level unless it is one of Droid's default allowed commands. A rule's tokens must be an exact, ordered prefix of a single plain command's; where Droid's matching cannot be told (a chained, substituted or redirected command, a glob or quote in the rule, a match narrowed by more than `prefix`) an allow or ask is not taken and the level decides, while a block is read loosely, anywhere in the command. A settings file that is missing, over 1 MiB or not JSON (comments allowed) adds no rules. This matching follows Factory's docs, not Droid's code, and has not been checked against a running Droid; which folder Droid takes as the project's is not verified either, and parent folders are not searched. MCP tools' levels are not in the payload, so an MCP tool never asks in the HUD. A decision is `permissionDecision` `allow` or `deny`; leaving it to the client answers nothing, and Droid's own prompt follows. Questions (`AskUser`), spec approval (`ExitSpecMode`) and `droid exec` runs stay with the client. A turn runs from `UserPromptSubmit`, renewed by `PostToolUse` and notifications, to `Stop`, or to the `idle_prompt` notification Droid sends instead when the user stops it; a `permission_prompt` or `elicitation_dialog` notification marks the session waiting. Droid matches no notification type, so each notification reaches every Notification hook. Droid reads its hooks when a session starts. Facts from Droid 1.3.0's code and docs.factory.com; not yet exercised with an installed Droid.

These are adapter implementations, not evidence that every client has been installed or exercised with a real account. Completion-only sessions are labeled `usageStatus: "unavailable"`; zero is a required wire sentinel, not a measured token total. Numeric statistics continue to use the canonical transcript ledger.

## Activation and platform status

The hook owner starts disabled. `connection.clientHooks` distinguishes supported transport, actual listener state, requested setting, installation eligibility, and installation state. Listening alone does not prove that client settings point at this app.

Configuration uses explicit `install_plan` / `apply_plan` with a host-delegated canonical executable. It preserves third-party hook entries, permissions and symlinks, rejects a stale plan, and refuses transient `target`/disk-image/translocated executables. A build of this repository alone has no delegated canonical hook executable, so Settings explains that installation is unavailable. No existing client configuration or original socket is acquired automatically. The old explicit `--install-completion-hook` and `--install-pi-observer` entry points report an unsupported-installation error instead of launching the UI or claiming success; the Pi observer extension itself has not been ported.

The inbox keeps the latest record of each kind per session, a running-turn observation (`Begin` events) included, which keeps the title its session's first prompt gave. It initially reconciles its history, then reads changed JSON files from filesystem notifications; directory/overflow notifications retain a full reconciliation fallback. A fixture with 2,000 records read one record for a single-file update, with no full scan.

Unix transport and isolated protocol fixtures are implemented. Windows requires a named-pipe callback/desktop adapter and remains unsupported; this is reported explicitly rather than emulated with macOS paths. Linux real-client qualification remains outstanding.

## Tests

Fixtures exercise client format and configuration vectors; isolated Unix callback round trips; connection withdrawal; changed hold deadlines; owner restart; pending Claude tool-result withdrawal; third-party configuration preservation, idempotence, symlinks and stale-plan refusal; Codex Desktop stream, patch and response receipts; and request projection without source scanning. A runtime fixture checks that request projection never consumes a usage record or wakes data collection, and that the collector advances the same ledger afterwards. Real client installation and a GUI hook-owner handoff are not covered by tests.
