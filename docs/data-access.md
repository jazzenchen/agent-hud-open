# Data access

## Overview

Agent HUD Open reads agent activity and usage metadata on your Mac. It has no Agent HUD account, cloud synchronization or push service. Building it requires no developer account, product credential, provisioning profile or signing certificate; local builds use ad-hoc signing.

## Providers

| Client | Local data | Quota or balance queries |
| --- | --- | --- |
| Claude Code | Session records, account profile, local session-origin hook records and Desktop session identifiers | Installed Claude engine usage interface |
| Codex Desktop / CLI | Session records and sign-in time, including `CODEX_HOME` | Installed Codex app-server account rate limits |
| DeepSeek Harness | Session records and the metadata of the process that holds a profile (Node, or the desktop app's Host on its own Electron), including `DSH_HOME`; its web host's pending questions on loopback | Official DeepSeek balance endpoint with the configured Harness API key, which Harness's own credentials package resolves inside a short-lived helper run by Node, or by the Harness desktop app's Electron in Node mode, whose package it then is |
| Antigravity | The process list (`ps`) and the listening port of the running language server (`lsof`), whose command line holds its local token, looked up at most every 10 seconds and at once when the server stops answering; conversation metadata | A local `POST` to that language server on 127.0.0.1; when only `agy` runs, whose own server takes a token it shows no other process, the running `agy` program's `agy -p /usage --output-format json`, which starts no turn and spends no quota |
| Cursor | Local application database and session metadata | Official Cursor usage endpoints with the installed client's session token; for an account that runs Grok Bot, Cursor's Grok Bot service for the routines of the rostered bots, with the same token |
| Grok CLI | Local session records and credential file | Official Grok CLI billing endpoint |
| OpenCode, Kimi, GLM, Pi | Local JSON/SQLite session records and supported provider configuration, including an `ANTHROPIC_BASE_URL` and its token from the environment or Claude Code's `settings.json` `env` that point at a Kimi or GLM plan; automatically prepared Pi lifecycle observer and OpenCode completion plugin | Official Kimi, GLM, OpenCode Go, and Pi ChatGPT quota endpoints where configured |
| GitHub Copilot CLI | Local session events and OpenTelemetry export files | GitHub Copilot quota endpoint with the GitHub CLI sign-in, only after consent in Settings |
| OpenClaw, Hermes Agent, ZCode, CodeBuddy, Qwen Code | Local session databases and transcripts | None |
| WorkBuddy | Local session transcripts; in `~/.workbuddy/workbuddy.db`, for the sessions a pass reports, their names (`sessions`) and what the app's own metering charged them (`session_usage`); and the GLM Coding Plan entries of its model list, `~/.workbuddy/models.json` | Official GLM Coding Plan quota endpoint with the key such an entry keeps |
| Qoder, Qoder CN, QoderWork | Nothing read; the approval hook is added to each build's settings | None |

Per-client fields, endpoints and stored data: [providers](providers.md). Token counts, percentages, alert levels, request intervals and reading retention: [usage semantics](usage-semantics.md).

## Credentials

- A provider that needs a key or token reads it from the client's own configuration, environment variables or local credential files, uses it only for that provider's usage request, and never includes it in reports or stored data.
- Claude and Codex quota queries use the installed clients' existing sign-in. Codex's ID-token sign-in time is read locally to choose the client that reads the account; its access and refresh tokens are not used. Pi ChatGPT OAuth uses the existing access token for the official usage endpoint, without using its refresh token or writing credentials. No request sends a model message or consumes a usage-reset credit.
- Account identity comes only from data a provider already reads or a response it already requests: the Claude profile, Codex `account/read` and Pi’s authenticated ChatGPT usage response, Cursor's local database, the Grok login record, Antigravity's local server and, for GitHub Copilot, GitHub's `/user` response. Provider user and workspace ids are stored as hashes; the account's email or name is kept locally to label its rows.
- GitHub Copilot quota reads no credential until the user confirms Settings → Agents → GitHub Copilot → Read quota; the dialog, shown each time it is switched on, names the environment variables, the keychain item `gh:github.com` and the GitHub CLI `hosts.yml`, and macOS may ask for keychain access. Switching it off forgets the account, its rows and its quota history at once.
- OpenClaw's agent database also stores authentication profiles; only its session tables are queried.
- Custom endpoints are not assumed to share official billing accounts, and executable key resolvers are never run.
- WorkBuddy's model list, `~/.workbuddy/models.json`, is read for an entry whose `vendor` is `GLM Coding Plan` and whose `url` is one of Zhipu's own coding endpoints. From such an entry the app takes its `apiKey`, the plan's key, used for Zhipu's official quota endpoint and for nothing else, its `url`, which says China or global, and its `id`, which a WorkBuddy call names when it goes through that entry, so that a plan the app reads from Zhipu shows its own windows instead of the ceiling a 429 of that call logged; nothing else in the file is read. An entry of another vendor, or at any other URL, a custom endpoint or Kimi's and OpenCode Go's included, is not read. A plan whose key only WorkBuddy carries is shown inside the WorkBuddy group, named with its provider beside it; the same key read from Pi or Claude Code too stays under GLM.
- Kimi account identity is confirmed through the official profile endpoint, separately for each deployment; only hashed credential-to-account associations are cached, and accounts are never merged from matching quota values, reset times or unverified token claims.
- DeepSeek session liveness inspection reads executable identity and start time. Question-host discovery reads command names, profile and port arguments; it does not read profile contents or browser credentials.

## Local storage

- Preferences use the application's UserDefaults domain, the panel's layouts among them with the Expanded panel's switches, which earlier versions kept in the settings and which are carried into the layouts once at launch; the usage ledger, the restart copy of the report and completion records live in `~/Library/Application Support/Agent HUD Open`. Local metadata can include workspace paths and session titles, and a title can be the first line of a prompt, cut to 60 characters; raw conversation bodies and authentication secrets are never stored.
- A log that a newer version of its reader reads again keeps the usage the earlier version recorded until the new read has covered the same times, so day totals, a session's breakdown and its share of a quota window neither drop nor count twice while its history is read again; once the log is read whole, only the new reading remains ([storage](providers.md#storage)). A session's own token count, on its panel row and in `LiveSession` for a host application, follows the new read and can be lower until the log is read whole. A log that shrank or was rewritten at the same size replaces what it recorded at once.
- WorkBuddy's ceilings still ahead, from the 429s its transcripts logged, are kept in `workbuddy-ceilings.json` in the same folder until their reset passes, so a monthly ceiling stays after its transcript falls out of the week a pass reads: each one's model, its window, its reset, when the 429 was logged and the id of the model entry the call went through, and nothing of the conversation.
- `~/Library/Caches/app.agenthud/instance.lock` keeps a second copy of the application from starting while one runs; it holds the path of the running copy's executable and nothing else.
- Quota, balance and account-wide usage requests run between local polls, one provider at a time and at most once a minute each: more often while that client works, every 5 minutes for a client nobody is using ([cadence](usage-semantics.md#collection-cadence)); a missing or signed-out client does not prevent other sources from reporting.
- Saved readings appear immediately after a restart with their original observation times; a failed refresh keeps them and reports the failure. Unavailable quotas are never inferred from token counts.
- Readings of an account a client is no longer signed in to stay until the account has not been seen for 30 days.
- A completed credential scan retires expired, removed or rejected OpenCode Go, Kimi and GLM quota rows, including cached rows and saved display settings.
- The approval hook adds one handler to a client's own settings or hooks file, leaving every other hook in it alone, and refuses to rewrite a layout it does not recognize. Codex CLI and Desktop share that handler; their hook trust and feature settings stay under Codex's control. ZCode runs no hook until its hooks switch is on, so an absent switch is set and one the user turned off is left off; a rewritten file keeps its permissions. Settings → General → Client hooks off removes Agent HUD's handlers from every client and adds none back; removing never creates a file the client did not have. What it carries — the tool, its input, the folder and the client's own rule suggestions — is read in memory to draw the card and is never stored; the answer goes straight back to the client that asked ([approvals](hud.md#approvals)).
- Codex rollouts that Codex compressed (`.jsonl.zst`) are decoded in memory by the app's own Zstandard decoder; the decoded text is read as a plain rollout is and never written. The app never compresses, decompresses, renames or deletes a client's files.
- Claude Code's compaction hook keeps one local record per session, its id, the time a compaction began and what started it, and nothing of the conversation; it runs without Claude Code waiting on it ([compaction hook](session-lifecycle.md#compaction-hook)).
- Optional completion hooks write one small local record per finished turn (session and turn identity, model, workspace folder name and time) and nothing else; they send no notifications and upload nothing ([completion hooks](session-lifecycle.md#completion-hooks)).
- Clawd's sprites, the Claude app's own, are bundled with Agent HUD and credited in `THIRD_PARTY_NOTICES.txt`; the application never reads the Claude app or its `app.asar` ([bots](hud.md#bots)). Only `scripts/clawd-sprites.py`, run by hand, reads an installed Claude app's `app.asar`, to copy the sprites into the repository.
- Claude and Codex origin hooks keep the latest session ID, host type, time and optional destination locally. They only report, so they are installed with `async: true` and the client never waits on them. They inspect the native callback process and never store its arguments or the hook's prompt. Claude Desktop navigation decodes only session identifiers and archive status from its Code and Cowork metadata; unrelated prompt, configuration and account fields are ignored. Shared Codex daemon navigation reads loaded thread IDs and the thread's local TUI endpoint through the running daemon, then matches its listener to a live Codex process of the current user. Only terminal identity variables are decoded; no model request or MCP tool is invoked, and navigation destinations are omitted from report caches and synchronization ([session navigation](session-navigation.md)).
- Pi's extension and OpenCode's plugin run inside those clients and write only metadata records of their turns — session and turn identity, workspace, the session's title, model, provider and times — beside the client's own data; they make no request and upload nothing ([observers](session-lifecycle.md#observers)).

- Antigravity approvals are read from its already-running local service, without changing its permission settings or installing a tool-execution hook. Only the user's explicit allow-once or deny sends an interaction answer to that same service; credentials and waiting tool inputs stay in memory. Client hooks off stops the observer.
- Codex Desktop Computer Use app approvals and browser approvals are read from the original thread owner's pending requests through `$CODEX_HOME/ipc/ipc.sock`. The HUD follows the threads that have a session in flight and keeps what their owners send in memory, with every string longer than 16 KiB left out as it is read, so screenshots, page contents and long tool output are never held; nothing of it is stored. Only an explicit HUD decision sends the native elicitation response, after checking that the same owner and request still wait; conversation and persistent scopes come from the request itself. Client hooks off stops observation. These requests are independent of the engine approval hook and its reviewer policy.
- Codex Desktop mid-turn questions are read from that owner's active turn messages over the same local IPC channel. Only the user's HUD answer is sent as Desktop's question-reply envelope to the unchanged active turn; Skip and expiry send nothing. Reading failures never establish that a question was answered. No conversation records are rewritten.
- The Claude desktop app's next-step box and offer card are read from the session log: the input of those two calls only: its question, recap and button labels with the words a button sends, held in memory only. The usage ledger keeps that the session waits, the call, its time and where its line starts in the log, and none of the words; after a relaunch that one line is read again for them. Agent HUD Open answers nothing: the app takes the click. Where the host can send words into the session, an answer given on the HUD sends the chosen button's message, or the user's own words, and nothing else.
- DeepSeek Harness's questions are read from its web host's loopback event stream and answered back on 127.0.0.1; only the answers the user gives on the HUD are sent, and nothing is written to Harness's files. Client hooks off stops the reading.

## Agent tools

- An AI agent reads and arranges the hover panel through the MCP server a person added to its client ([command line](command-line.md#mcp-server)). Settings → Experimental adds it to Claude Code or Codex by running that client's own `mcp add` or `mcp remove` when the person picks the client in its menu; otherwise Agent HUD only reads the client's configuration, `mcpServers` in `~/.claude.json` and `mcp_servers` in `~/.codex/config.toml`, to show whether the server is there. The server has five tools, all about the hover panel, the resting HUD and, when the person asks for one, the app's own settings, and every answer comes from what the running application already holds: no tool starts a provider read or a request to any service.
- `get_hud` returns each block's key, a vendor id or `api:` and an API provider, and its name; each block's accounts, each by its id, the hash Agent HUD already stores for a quota account (`ProviderAccount.id`: `account:`, or for a billing pool's plan `pool:`, and 64 hexadecimal digits) or an API account's pool id or vendor (`APIBilling.id`), with the email or name its provider gave, as the panel writes it, the account's plan, and whether it is the client's signed-in account; each quota window's key and name, the account it belongs to, the name in the application's language as the panel writes it, share used to a tenth of a point, level, reset time, the state of its reading (`normal`, `stale`, `read failed` and the like), burn rate, the time it runs out when that is before its reset, and tokens per hour; each API balance's currency, amount, level, state and the time it runs out at the pace it fell over the day before its reading, and over its block's period the estimated cost of the requests Agent HUD recorded for its account, that cost per day and the time the balance runs out at that pace, worked out from the costs the application already holds; and the layout in effect and the style it sets, the panel's width among it, how each block is drawn and which measures it offers, whether it is an unsaved draft, the panel's height on its display and whether it scrolls there, which sections it shows and whether the quota blocks show reset countdowns; how far back a quota block's chart and an API balance's estimated cost, burn rate and chart reach; for the session rows, the limit, period, order, agents, projects and states in effect, the agents that have sessions now and the projects those sessions belong to, each by its folder written with ~, such as `~/Development/agent-hud`, or `unassigned`, and its name, how many rows are shown and how many more the filter keeps, and how many of the period's sessions wait, run and have ended, as counts; for the token chart, its period, its agents and models, the agents whose models it can draw, the models it can draw, each by its id, such as `claude-model:claude-opus-5-5`, with its name and its agent, and the tokens it counts over that period; and each attached display by its key, a UUID the system gives the display, and its role (`Built-in display`, `Main display`, `Display 2`), never the name the system or its owner gave it, with its HUD's mode and edge, whether it has a notch, whether it uses the shared layout or its own, its resting HUD's style in effect, its placement, look and glow as numbers, switches and names, the look it draws now with whether macOS is light and Reduce Transparency is on taken into it, whether a style draft waits, the agents its resting HUD can show, by vendor, the width one agent's own panel has there, and whether an agent's edit holds its panel open and for how many seconds more; and what the whole app's own settings draw now, an unsaved draft of them included, and whether one waits: its Appearance and Match screen, Bot logos, whether the menu-bar icon shows, the language chosen and the one the panel's names are written in, and whether hovering takes Option, whether the top edge opens the panel at once and the hover and collapse delays. The result goes to the client that called, which passes a tool's result on to its model.
- Agent HUD Open runs on a person's own Mac for that person, and the tools answer only while that person has them on, so the agent they ask may know the accounts and the projects they work with and what their API accounts spent, which it needs to choose the accounts a block shows, to narrow the session rows to some projects and to choose how a balance is drawn; none of them used to be told. `get_hud` names each block's accounts by the email or name a provider gave, which the panel itself shows, and by the id Agent HUD keeps it under, by which a proposal chooses them. It names no session title, prompt, session id or conversation text, and no credential; sessions reach it as counts, their agents' names and their projects. A project is named by its folder written with ~ and the folder's last part, a Git repository by its common root, so that its worktrees are one project, as the statistics window's Sessions page groups them, and nothing else of the folder a session ran in is told. A session's project is found from Git's own pointers, the `.git` in its folder or a folder above it and a worktree's `commondir`, once for each folder a report names, and a path an agent names in `sessions.projects` is read the same way; that is no provider read, and nothing else on disk is read for it. A window's name is its vendor's own wording, which for some vendors carries the name of the plan. Wallet amounts, earned resets, token history by column and a quota window's list cost are not part of it; the token chart's total over its period is, and so is an API balance's estimated cost over its block's period with the pace it sets, as the panel shows them.
- `get_hud_screenshot` returns a PNG picture of a screen's whole hover panel as the layout in effect there draws it, drawn off screen in the application without opening the panel. It shows what the panel shows, numbers, window names, plans, reading states, balances, wallet amounts, earned resets, costs, the token chart and the session rows' marks, states and token counts, with three things hidden: each account's name is masked to the first and last character of the part before any @, three asterisks between and the domain kept (`j***s@gmail.com`, `P***l`, `***` for a name of one or two characters); each session row is named by its place, Session 1 and so on, in place of its title and project, with nothing else written from a session's title, path or prompt; and text a provider or a client wrote, a reading's reason and a client's notice, which can quote a path, an account or whatever a process printed, is drawn as placeholder bars in its place. Where a reading came from, which an account's information mark tells on hover, is not in it, and neither are the island's alerts, a question's text or the line about a failed refresh. The picture, with a short text that says what it shows, goes to the client that called and on to its model like any tool result. The panel a person sees masks nothing. With `agent` it is a picture of one agent's own panel, the card a dock that separates its agents opens beside that agent's mark, which shows that agent's blocks, session rows and token chart alone and is masked the same way. With `show` `hud` it is instead a picture of one screen's resting HUD as it looks now: the island and its glow, a dock's marks, or a Simple panel's marks with their rings, percentages and balances, which name no account or session.
- `draft_hud` and `discard_hud_draft` change unsaved drafts alone: the draft of the shared layout or of one screen's own, a screen's style draft with it, and, through `draft_hud`'s `app`, the app's draft of its own settings, its Appearance, Match screen, Bot logos, Show menu bar icon and Hover behavior, which an agent is told to propose only when the person asks it for that setting and which no drop of a layout's draft touches; each lives in memory until a person presses Save in the panel. A draft can change what that screen's panel and resting HUD show at once, its mode, edge, sizes, look and glow included, and the app's draft how every HUD's marks and hover, the app's windows and the menu-bar icon behave at once; the bar with Save and Discard stays in every screen's panel while it waits, so a draft that hides the menu-bar icon leaves the person a way back. While an agent edits a layout, its calls hold that screen's panel open on screen for two minutes after the last of them, without a provider read, until the agent calls `finish_hud_edit` or the person does anything on the HUD or clicks elsewhere ([panel holds](hud.md#panel-holds)); the hold is kept in memory alone. No tool saves a layout, writes the settings, or changes a screen's saved placement or glow, the agent list or an account: only a person's Save writes a style draft or the app's draft into the settings, and a person's own edit of that screen drops its style draft, and of one of the app's settings that field of the app's draft. The language is changed in Settings alone. The four switches of Settings → Display → Expanded panel are fields of the layouts, which a draft sets and only a person's Save keeps, and which a person's switch there sets in the layout the display chosen there keeps saved, its own or the shared one. The saved layouts and the ones before them, with a screen's placement and glow in the version before, are kept in the preferences, under display keys, and name blocks, windows and agents by key and vendor, accounts by the id Agent HUD keeps them under, never by email or name, and projects by their folder written with ~ ([panel layout](hud.md#panel-layout), [style drafts](hud.md#style-drafts)).
- The application answers tool calls on `mcp.sock` in its data directory, a unix socket that only this user can open and no network port, and only while Settings → Experimental → Let agents arrange the HUD is on, off by default; while it is off the socket is closed. A demo answers them only when started with `--demo-tools` before any other copy, and then from the sample and the demo's own preferences; a real copy started while it runs answers none. It does not tell callers apart: any process running as the same user can connect and call the same five tools, whether or not an MCP client started it. The `--mcp` process itself makes no network request and reads no provider data; it reads the instance lock, without taking it, to say whether the tools are off or the application is not running.
