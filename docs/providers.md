# Providers

## Overview

A provider is the `AgentHUDCore` component that turns one client's local records and account queries into a `UsageReport` and the usage ledger: sessions, token events, quota windows with the account they belong to, balances, turns and completions. Common rules: a provider reads only what the client already stores on this Mac; it uses the client's existing sign-in or configured key for metadata requests only, never sending a model message or consuming a reset credit; credentials never enter reports or stored data; a provider says what went wrong with a reading as a failed read — a request that failed, Claude Code's engine failing or its account changing during a read, Antigravity not running, GitHub Copilot without a token — or, for a Kimi, GLM or OpenCode Go pool whose account it could not confirm, as unverified, while what a successful answer left out, such as Grok's used credits or a Cursor plan's percentage, and a Claude Code login without plan limits, is only a notice shown under the client. Notices and issues keep their vendor, account or client-home scope; a failed login never becomes another client's notice; network requests follow no redirects and share no cookies; SQLite databases are opened read-only in one read transaction, which sees committed WAL pages; a WAL database whose writer removed its `-wal` and `-shm` files on close, which a read-only connection cannot recreate, is read as an immutable file when no WAL or rollback journal is beside it, failing if the file changes during the read; a missing, signed-out or failing client never hides another. Counters a record names as cache writes or reasoning are kept as those kinds within In and Out. A session's title is the one its client keeps — a name the user gave, else one the client generated — else the first line of its first prompt, else its workspace folder; a placeholder a client writes until its title arrives is no title, and a title keeps its first line and 60 characters. Counting conventions and request intervals: [usage semantics](usage-semantics.md); running and terminal turns: [session lifecycle](session-lifecycle.md); boundaries: [data access](data-access.md); probes: [command line](command-line.md).

## Claude Code
- **Reads** — `~/.claude/projects/**/*.jsonl` and `~/.config/claude/projects/**/*.jsonl`; `~/.claude.json` (`CLAUDE_CONFIG_DIR` honored) for the Max tier, the account ids and the email label, read before and after each engine query — a login change in between discards that reading. A session's title is its last `custom-title` line (the name the desktop app generated or `/rename` gave), else its last `ai-title` line (one Claude Code generated), else the first line of its first prompt; title lines carry no timestamp.
- **Credentials & env** — The installed engine's existing sign-in; nothing is read from the keychain. `rate_limits_available == false` keeps local data, makes no account current and names the reason beside the account: `claude auth status` tells a signed-out engine, which asks for a new sign-in, apart from an API-key or third-party login, which has no plan limits to read.
- **Endpoints** — A headless `claude -p` — the engine at its install places (`~/.local/bin`, `~/.claude/local`, Homebrew, `/usr/local/bin`, the desktop app's newest `~/.local/share/claude/versions`), else the first on `PATH` — with hooks disabled and `CLAUDE_CODE_ENTRYPOINT=agent-hud` answers one `get_usage` control request with `skip_behaviors`, which spares it a scan of the week's transcripts (engines without the flag ignore it); no prompt is sent, nothing is billed. `five_hour`, `seven_day` and per-family weekly windows become rows `claude-session`, `claude-weekly` and `claude-weekly-<family>`, of which only a family's weekly window limits some models rather than all (`AgentDescriptor.allModels`); `subscription_type` `max` is refined to `max_5x` / `max_20x` from the profile's rate-limit tier.
- **Counting & dedup** — One event per `message.id` (fallback `requestId`) in the log named after the line's own `sessionId`: a forked session's log begins with its parent's lines, which keep the parent's session and times, and they neither count nor title or start the fork. A session log found in several project folders, as when a session is resumed after its repository moved, is read from its most recently modified copy only. In = `input_tokens` + `cache_creation_input_tokens` (the cache writes), Out = `output_tokens` with `output_tokens_details.thinking_tokens` as reasoning, Cache = `cache_read_input_tokens`; consumers are exact model ids, and `<synthetic>` messages are ignored. `isSidechain` lines, which older builds wrote into the main log for their sub-agents, never start or finish a turn; a sub-agent transcript (`agent-*.jsonl`, `subagents/`) follows its own turn, which keeps its session running, and records no completion or prompt ([sub-agents](session-lifecycle.md#sub-agents)). Prompt lines mark turns and `compact_boundary` lines compactions; the summary a compaction writes is not a prompt. The session share is the session's share of the current 5 h window times its utilization; `entrypoint` labels CLI, Desktop, IDE or SDK through the vendor catalog, and one the catalog does not name is shown as written.

## Codex Desktop / CLI
- **Approvals** — Both clients use `PermissionRequest` in `$CODEX_HOME/hooks.json` (default `~/.codex/hooks.json`), with one `--permission-hook codex` handler installed at HUD startup when the Codex home exists. Codex runs the hook before choosing automatic or manual review. The HUD offers allow-once and deny only when the last `turn_context` matching the request's `turn_id` in its `transcript_path` explicitly names `approvals_reviewer: user`; automatic review, an unconfirmed reviewer or an unreadable record returns no hook answer and leaves Codex's own approval flow in control. The hook never supplies an automatic allow. Codex does not persist reviewer changes during a running turn, so a mid-turn mode switch may differ from the recorded reviewer until the next turn. Allow-once and deny use the shared hook channel; `apply_patch` displays the supplied patch. Permission-rule updates are unsupported. Codex must support [permission hooks](https://learn.chatgpt.com/docs/hooks#permissionrequest), with hooks enabled and the exact handler reviewed and trusted in Desktop hook settings or CLI `/hooks`; the HUD never writes trust or overrides disabled hooks. Existing JSON hooks and inline TOML hooks are preserved.
- **Pi ChatGPT accounts** — `openai-codex` OAuth in Pi `auth.json` supplies its existing `access`, `accountId` and millisecond `expires` to `GET https://chatgpt.com/backend-api/wham/usage`, with bearer authorization and `ChatGPT-Account-Id`. The authenticated response supplies `email`, `account_id`, `plan_type`, `rate_limit` and `additional_rate_limits`; window IDs match the engine mapping. No refresh token is used or written; expired logins ask the user to sign in through Pi. Native and Pi logins of the same email/workspace produce one window inventory, history sample and event, displayed under Codex. The latest known sign-in chooses the client that reads the account; a login without a reliable sign-in time keeps that confirmed reading client while its home is still configured. Polls, failed requests and automatic token refresh never change ownership; separate accounts retain their own notices and reset credits.
- **Reads** — `rollout-*.jsonl` under `$CODEX_HOME/sessions` and `archived_sessions` (default `~/.codex`), decoding only `session_meta`, `turn_context`, `event_msg` and `compacted` lines; `session_index.jsonl` for thread names. A session's title is its thread name, else the first line of its first own prompt (the text parts of an `item_completed` `UserMessage` item, or a legacy `user_message`), else the final component of a spawned agent's path, else its nickname, else the workspace folder. A spawned agent's display name is its source nickname, else the final component of its agent path.
- **Credentials & env** — The engine's own sign-in supplies quota. Only the ID token's `auth_time` in `auth.json` is read to choose the account's reading client; no native access or refresh token is used. Pi's access token supplies `auth_time` when present. Token issuance and file modification times are not sign-in times. Desktop and CLI on one `CODEX_HOME` share one login.
- **Endpoints** — `codex app-server --listen stdio://` (the engine bundled with the desktop app, `Contents/Resources/codex-cli/bin/codex` or in older builds `Contents/Resources/codex`, found under its known app names or, whatever the app is called, by its bundle ID `com.openai.codex`; else an installed CLI): `initialize`, `initialized`, `account/rateLimits/read`, `account/read`, never a thread or turn. Members of one workspace share `accountId`, so the email separates their quota; an engine without `account/read` reports the workspace alone, and some installed CLIs leave out `accountId`. `account/read` gets two seconds after the limits. A reading it answers too late keeps the email that workspace last came with on the same home, and a reading without `accountId` keeps the workspace its email last came with there, unless that email came with several; both are remembered across launches, so the account keeps its key. A reading with both names the keys it would have without either, whose earlier readings then leave. `rateLimitsByLimitId` is authoritative even when empty; each bucket's `primary` / `secondary` window is a row named as Codex's own client names it by `windowDurationMins`: 5h, Daily, Weekly, Monthly or Annual limit within 5 %, else Nh or Nm limit, and without a length Usage limit or Secondary usage limit. A bucket other than `codex` puts its `limitName` before that as the vendor catalog names it (`gpt-reserve` → Luna Reserve, the name OpenAI's own client shows) or else as the service sent it, and is known in short by the catalog's word for it (Reserve) or else the name's last word without version numbers and GPT, Codex or Claude (GPT-5.3-Codex-Spark → Spark). The shared primary row keeps the window name `codex`, only the `codex` bucket's windows limit every model (`AgentDescriptor.allModels`), `planType` (else the `account/read` plan) is the plan badge and `rateLimitResetCredits.availableCount` the reset-credit count.
- **Counting & dedup** — `token_count` totals are differenced (`total_token_usage`, `last_token_usage` after a reset); cached input is subtracted from input, `cache_write_input_tokens` are the cache writes, `reasoning_output_tokens` the reasoning already in output, `model_context_window` the call's context window, and inherited fork history only sets the baseline: events before the session start, or through the inherited-history ordinal recorded in the first metadata. The first valid session metadata owns the rollout's identity; copied parent metadata never replaces it. `task_started` marks turns and `compacted` lines compactions. `source` `cli` or `exec` decides the client; otherwise `originator` names it through the vendor catalog (`Codex Desktop`, `codex_work_desktop` from the desktop app signed in to a work workspace, and `codex_desktop` → Desktop; `codex_vscode` → IDE; `codex-tui`, `codex_cli_rs` and `codex-cli` → CLI; `codex_exec` → CLI · exec), an originator the catalog does not name is shown as written, and a `vscode` rollout without one is the IDE extension; `subagent` and `guardian` sessions stay outside the top-level session list; spawned agents appear within their parent's detail: their rollouts name the thread that started them (`parent_thread_id`, in the spawn source or beside a guardian's), and a session's breakdown takes every rollout below it. One session id counts once even after archiving.

## DeepSeek Harness
- **Reads** — `$DSH_HOME/sessions/**/session[.vN].jsonl[.zstd]` (default `~/.dsh`) in Harness session formats 0 and 2–4, where a newer format is reported as unsupported; `profiles/*/cordis.yml` only as process evidence; `settings.yaml` and `.credentials.yaml` for the balance key. Node.js is required for Zstandard frames and the balance helper; a compressed log that grew is decoded from its last complete frame, and a plain one read from where the last read stopped.
- **Credentials & env** — `settings.yaml` section `llm-deepseek` names `apiKeyEnv` (default `DEEPSEEK_API_KEY`) and `baseURL` (`DEEPSEEK_BASE_URL` also honored), and the environment wins over the stored reference. The key is resolved by Harness's own credentials package inside a short-lived Node helper and never leaves it; any origin other than `https://api.deepseek.com` reports a custom endpoint without a request.
- **Endpoints** — `GET https://api.deepseek.com/user/balance`; balances decode as `Decimal` and keep their currency. Requests of provider `deepseek-official` are priced per model in CNY and USD from the official price list, ×2 in peak hours (Monday–Friday 09:00–12:00 and 14:00–18:00 Beijing time); unpriced models or other routes have no estimate rather than zero.
- **Questions** — Only web hosts exposing the confirmed `host.describe` and question event-stream API are connected. The host is found in the process list (`--port`, else the default 3080) and confirmed before opening `ws://127.0.0.1:<port>/api/events.mux`; a `question/requested` frame carries the questions and `question/resolved` closes them. An answer posts to `/api/respond` under the original question ids, with exact selected labels and optional custom text kept separate; a skipped question has an empty selection and absent custom text is omitted. The card settles after an accepted receipt, an explicit `not-pending` receipt, or the host's resolution event; failed sends and other rejections can be retried. Plan reviews and questions carrying supporting detail stay in Harness so that their full content can be read. Hosts using the newer authenticated Typert Remote API remain on their native UI: their API is different, and this integration neither reads launch tokens or browser cookies nor connects to it.
- **Counting & dedup** — In format 0, `assistant/chunk` usage and the following `assistant/message` usage describe one attempt (turn, step) and replace each other, and `llm/retry-started` opens a new attempt; from format 2, each `assistant/message` (its `usage`) and each failed `assistant/attempt` (the last usage chunk of its embedded stream) is one attempt. In = `inputTokens` + `cacheWriteTokens` (the cache writes), Cache = `cacheReadTokens`, Out = `outputTokens` (reasoning included, as `reasoningTokens` where logged); `turn/start` marks turns. Inherited history only sets the model: lines before `seedLength`, or in a seeded format-2+ log the lines before the fork's own `session/end-seed` with `inherited: true`, the last such marker (markers copied from ancestors are followed by more inherited lines). Formats 2–3 write that marker at or after the header's `createdAt`. Format 4 dates it, and the closers of an inherited turn the fork cut open (`turn/end` reason `forked`), at the last inherited line; the fork's first line from `createdAt` on then settles the cut, leaving the closers inherited.

## Antigravity
- **Reads** — SQLite `gen_metadata` (and `steps`) in `$GEMINI_CLI_HOME/antigravity-cli/conversations/*.db`, `antigravity/*.db` and `antigravity/conversations/*.db` (default `~/.gemini`); same-named databases in different roots are one conversation. A conversation's title is the `title` in `annotations/<id>.pbtxt` beside its folder, which agy generates when the conversation starts and a rename replaces; headless runs have none.
- **Conversation text** — `AntigravityConversation` reads visible user-input and planner-response text from `steps.step_payload` protobufs in a committed read-only SQLite transaction, including WAL writes. It excludes reasoning and tool arguments, keeps the original step index as the turn identity, and uses recorded timestamps. The existing native conversation navigation remains available.
- **Credentials & env** — None read. The running language server's CSRF token is taken from its command line; no login is attempted, and a self-signed certificate is accepted only for 127.0.0.1.
- **Endpoints** — `POST https://127.0.0.1:<port>/exa.language_server_pb.LanguageServerService/RetrieveUserQuotaSummary` (Connect protocol) on the user's `antigravity-cli` / `agy` or application `language_server` process, falling back to `GetUserStatus`. Every quota refresh sends `forceRefresh: true`, as Antigravity's native quota popover does, so the local server refreshes its cached summary. `GetUserStatus` on the same server supplies `email` and `teamId` for the account, since the IDE and `agy` can be signed in separately; its older per-model readings never replace retained summary windows of the same account. Legacy rows already in a restart cache also retire while that same account has summary windows still present. A successful summary explicitly lists that account's complete enabled bucket inventory: omitted or disabled buckets retire immediately, an enabled bucket without a new percentage keeps its last reading, and an identified account's empty inventory retires all its windows. Legacy fallback makes no completeness claim. Buckets (`bucketId`, `remainingFraction`, `resetTime`) become rows `antigravity:<bucketId>`, named `<group> · <bucket>` as the server writes them, with the period inferred from "weekly" or "five hour" / "5 hour" in the id or name, whatever the case and with `_` or `-` between the words, as in Antigravity's Weekly Limit and Five Hour Limit. In short, one group's windows are their periods; with several groups a window is its group's first word, third-party for Claude and GPT models, followed by its known period even when that group has one window. Retained summary windows use their recorded duration for the same compact names. With several groups, or several families in the legacy status, each window limits its group's models (`AgentDescriptor.allModels`). The legacy status yields one row per model family, Gemini Models and Claude and GPT models by Antigravity's names and any other model by its label, and the plan is `userTier.name` or `planStatus.planInfo.planName`.
- **Counting & dedup** — `ModelUsageStats` supplies the counters: In = input + cache write, Out = the recorded output total (thinking included), Cache = cache read; model identifiers are never token counts. Model-only failed retries record no usage and are skipped. A nonzero usage row counts only with a recorded timestamp or a unique join to a `steps` row via message or execution ID; file times are never usage times, and unverifiable usage is excluded with a notice. Identity is the response id or the row index.

## Cursor
- **Reads** — `ItemTable` keys `cursorAuth/accessToken` and `cursorAuth/cachedEmail` (the account label) in `~/Library/Application Support/Cursor/User/globalStorage/state.vscdb`. For the conversations the usage events name, only their titles: the `name` of an IDE composer's row in the same database's `composerHeaders`, else the `title` of an agent CLI chat's or ACP session's `meta.json` under `~/.cursor/chats/*/<id>/` or `~/.cursor/acp-sessions/<id>/`, where a chat still called New Agent has none. A conversation run on another machine or in the cloud keeps `Cursor · <id>`.
- **Credentials & env** — The JWT must stay valid for at least 60 s; `sub` supplies the user id and the `WorkosCursorSessionToken` cookie is built in memory. Nothing is refreshed or written; an expired token is a sign-in notice until Cursor renews it.
- **Endpoints** — `GET https://cursor.com/api/usage-summary` → rows `cursor`, `cursor:models`, `cursor:third-party`, `cursor:personal`, `cursor:team` and `cursor:extra`, named in Cursor's words Included usage, Cursor Models, Other Models, Individual spending limit, Pooled usage and On-demand usage, of which the two model pools each limit some of the plan's models (`AgentDescriptor.allModels`), with the period from `billingCycleStart` / `billingCycleEnd` and `membershipType` as the plan. `POST https://cursor.com/api/dashboard/get-filtered-usage-events` from the start of the day at least 7 days back, paged, with `totalUsageEventsCount` required to agree between pages.
- **Counting & dedup** — Rows without `tokenUsage` are skipped; In = `inputTokens` + `cacheWriteTokens`; identity = hash(account, `conversationId`, timestamp, model, counts) plus an occurrence ordinal, so true duplicates survive and rows seen from another Mac merge. Events group into `cursor-account:<account>:<conversationId>` sessions that are account-wide, never running and not attributed to this Mac.

## Grok
- **Account and clients** — Grok owns the account and quota windows. Grok CLI and Grok Bot are separate execution clients with independent names and artwork; Grok Bot is detected by its `com.anysphere.sand` application or `~/Library/Application Support/Grok Bot` directory. Bot installation does not establish CLI installation. User-confirmed account links in the app's local `grok-account-links.json` map a hashed Bot cache-account id to its CLI account id. A linked personal Bot reading supplies one quota under that account and retires its earlier cache-slot row. A unique personal login identity preserves the link after CLI token expiry; a `User` principal can include a `team_id`, while ambiguous or `Team` login records cannot confirm it. Unlinked identities remain separate. Bot sessions are read from the current account's local cache; live turn state remains unavailable.
- **Bot quota** — A valid schema-2 personal quota cache keeps its original `readAtMs`, reset and allowance. For a linked account it is read directly, so a proxy request's completion time cannot replace it with a different backend's allowance; the CLI proxy remains the fallback when the native reading expires or disappears. Selected teams, expired readings and account switches cannot reuse another account's reading. No Bot auth, encrypted profile or Keychain item is read.
- **Reads** — `$GROK_HOME/auth.json` (default `~/.grok`), `sessions/**/updates.jsonl` with `summary.json` / `signals.json`, and `logs/unified.jsonl`. A session's title is `summary.json`'s `generated_title`, which Grok keeps current and a `/rename` pins, else the workspace folder.
- **Navigation** — CLI `active_sessions.json` links an exact session to a live native process. An unambiguous interactive iTerm process with a verified pane identity can reveal that existing pane; stale, headless, multiplexed or ambiguous records supply no destination. Bot uses its native `grokbot://app/v1/agent?id=<agentID>` route.
- **Bot cache** — The current `account-slot`, its schema-4 `roster.last-roster`, and schema-1 `transcript.replicas.<agentID>` slices under `sand-client-persistence` supply account-scoped session metadata and visible user/assistant text. Schema-2 `weekly-usage.cache` supplies personal included usage and on-demand amounts for up to 24 hours, retaining its read timestamp; a valid reading without a usage percentage remains unavailable, and team-scoped readings need a live selected-team response and are omitted. Healthy cache provenance is informational source detail. Blob filenames encode slice keys as Base32; long keys have a key header. The conversation cache is bounded and is not complete history. `GrokBotConversation` preserves message identity and sequence gaps, omits widgets, tools and reasoning, and reports no inferred turn completion. Account changes invalidate cached readings instead of exposing another account's data.
- **Bot usage** — A unique Cursor dashboard conversation joins a unique current-account Bot session when its `conversationId` equals the Bot's native agent ID, regardless of model name. The combined report keeps Bot's session identity, title, transcript and navigation, and references Cursor's original ledger contribution for account-wide tokens, model breakdowns and calls; the separate Cursor display row is removed. The execution session remains Grok-owned for client controls and conversation routing. Bot's native `sand-subagent-` namespace also establishes a Bot execution client without roster membership. These billing-only records keep their original accounting IDs but stay outside the top-level Sessions list unless native transcript or navigation metadata establishes a conversation; known child relationships remain in their parent's detail. This applies to restored reports that previously labeled them Cursor too. Events, account attribution and model consumer IDs stay in the Cursor source and count once, including in its billing statistics. Other unmatched or ambiguous rows remain Cursor sessions. Billing model identifiers such as `grok-bot-default` do not identify the underlying serving model; no Cloud Agent parent/child relationship is inferred.
- **Credentials & env** — An `auth.json` entry keyed `https://auth.x.ai::…` (preferred) or `https://accounts.x.ai/sign-in` with a non-empty `key` and an unexpired `expires_at`; `principal_type` `team` is rejected with a notice; the entry's `user_id` (else `principal_id`), `team_id` (else `organization_id`) and `email` name the account, with credential evidence. Browser cookies are never imported.
- **Endpoints** — `GET https://cli-chat-proxy.grok.com/v1/billing?format=credits` (Bearer token, `x-xai-token-auth: xai-grok-cli`): `creditUsagePercent` and `currentPeriod` (weekly / monthly) make the `grok` row, Weekly or Monthly usage limit as xAI names it, else Usage limit. Missing usage remains an explicit unavailable reading with the reported reset and period. `onDemandCap` / `onDemandUsed` define the separate `grok:extra` percentage only with a known usage and positive cap; `/v1/settings` supplies `subscription_tier_display`.
- **Wallets** — `prepaidBalance`, `onDemandCap` and `onDemandUsed` are USD cents in the official [xAI `Cent` contract](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-shell/src/extensions/billing.rs). A present empty `Cent` object is its protobuf zero; an absent or invalid value is unavailable. Bot `usedCents` / `limitCents` have the same units. Wallet amounts stay separate from subscription usage. A confirmed personal account link permits a short billing read to supplement a native quota, selecting each wallet's newest observation without mixing accounts or refreshing the native timestamp. Cancellation propagates; a failed supplemental read leaves the valid native quota available.
- **Counting & dedup** — `updates.jsonl`: `session/update` events whose `sessionId` matches the directory, deduplicated by `_meta.eventId`, turn from `_meta.promptId`, usage from `turn_completed` (cached reads subtracted from input). `unified.jsonl`: `shell.turn.inference_done` with `prompt_tokens`, `completion_tokens` and `cached_prompt_tokens`, model scoped to session and process, identity `event_id` or a line hash; it owns usage for sessions it covers, the legacy log keeps titles, turns and completions, and legacy `totalTokens` context counters are not consumption.

## OpenCode and OpenCode Go
- **Reads** — `opencode.db`, then `storage/message/**/*.json`, under `$XDG_DATA_HOME/opencode` (default `~/.local/share/opencode`): a session's replies come from `session_message` once that table holds any of them, else from `message`, because the two name one reply by different ids; titles come from `session_v2` / `session`, where the `New session - <time>` or `Child session - <time>` placeholder a failed title call leaves gives way to the workspace folder. `agent-hud/turns/*.json` written by the plugin carry completions only, and their title counts only when the database has none. `auth.json`; `$XDG_CONFIG_HOME/opencode/opencode.json[c]` for `provider.<id>.options.baseURL`.
- **Credentials & env** — `auth.json` entries of type `api`: `opencode-go` (Go), `kimi-for-coding` / `kimi-coding` / `kimi-code` (Kimi CN), `zai-coding-plan` (GLM global), `zhipuai-coding-plan` (GLM CN); a configured `baseURL` must be an official coding endpoint to count as a plan, and OpenCode's own `zai` provider is not one. `OPENCODE_GO_API_KEY` is Go; keys for known API hosts become API service rows without a balance query.
- **Endpoints** — `GET https://opencode.ai/zen/go/v1/usage` per pool: `rolling` (5 h), `weekly` (7 d) and `monthly` with `percent` and the ISO timestamp `resetsAt`, named 5-hour limit, Weekly limit and Monthly limit as OpenCode names them.
- **Counting & dedup** — Assistant messages with a `tokens` object: In = `tokens.input` + `tokens.cache.write`, Out = `tokens.output` + `tokens.reasoning`, Cache = `tokens.cache.read`; consumers are `opencode-model:<model>#<provider>`, named by `ModelCatalog.consumerName(of:)` as the model with its provider beside it, priced at the model's list price when `provider` is the vendor's own API or plan, never by the message's own `cost`. Both stores yield the id `opencode:<message id>`, so a message present in both counts once.

## ZCode

## Billing pools

`BillingPool` identifies who pays, independently of the program that made the request: `provider` (Kimi, GLM, OpenCode Go), `realm` (CN, International), `product` (plan, api, unknown), `scope` (account id from Kimi `/me` or a credential hash, never the credential), `evidence` (account, credential, unresolved), `organization` / `project` (GLM team) and `entitlement` (`kimi-code`, `glm-coding-plan`, `opencode-go`). `id` is `pool:` plus a hash of all fields and doubles as the account id; a window row is `<pool id>:<window>`, and windows of one pool are never added together.

- Identical credentials found in Kimi, OpenCode, Pi or Claude configuration merge into one pool with several clients; a different key stays a different pool until the provider's own identity protocol proves otherwise, and only Kimi has one. Same plan name, reset time or percentage never merge pools.
- Each pool's quota is fetched once per interval with any of its credentials; when every credential is rejected the pool is inactive and `UsageReport.activeQuotaPoolIDs` retires its rows, readings and display settings, while a temporary failure keeps the last reading. A failed reading, or an identity the provider could not confirm, is the pool's own notice: it is shown under its vendor, OpenCode Go's under OpenCode Go, and holds back that pool's rows alone.
- Historical usage keeps the attribution recorded at the time (`UsageAttribution`); events without a pool are shown as billing unconfirmed and never re-attributed from today's login. Claude quotas come from its own engine. Codex combines its engine read with Pi ChatGPT OAuth usage reads, merging only the same authenticated email and workspace into one account; Pi token events remain owned by its transcripts.

## Storage

Files in the data directory ([architecture](architecture.md#storage)). None contains credentials, and the only conversation text in them is a session's title, which can be the first line of its first prompt, 60 characters at most.

| File | Contents |
| --- | --- |
| `usage-ledger.sqlite` | Per log file the client's parse position and session summary, or the sessions of a file parsed whole; token events grouped by session with their estimated cost and, where logged, their context window; the prompts and compactions of each log; the 15-minute usage and cost totals kept exact as events arrive, change or leave; the largest prompt each model was seen with; quota readings per provider; the last day of API balance readings per currency |
| `last-usage-report.json` | The retained report without turns and completions, restored at start; rewritten at most every 5 minutes |
| `engine/`, `turn-completions/<source>/`, `attention/<source>/`, `open-agent-identities.json`, `codex-identities.json` | Claude Code engine working directory; the completion-hook inbox; the notification-hook inbox, holding each session's pending request and the client's own notification text; confirmed Kimi identities as hashes; the email each Codex home's workspace last came with, by home and workspace hash, and each ChatGPT account's confirmed reading client and available sign-in time |

- An appended log is read from where the previous read stopped; a file that shrank or was rewritten is read again and replaces what it recorded, and so is every log of the last 31 days whose saved state an earlier version of its reader wrote.
- A file missing from its client's listing removes what it recorded, also when its directory is unreadable or gone; a listed file that cannot be read keeps it, as does one the read budget has not reached. A log or database whose read failed is read again only after a pause that doubles from 30 s to 5 minutes, whether or not it changed meanwhile, and it does not count as still being indexed.
- A JSON Lines log parsed whole is read up to 256 MB within 3 seconds, or the read counts as incomplete; a line over 16 MB that its reader does not decode, such as a large tool result, is skipped.
- Copies of one session in several places, such as a Codex rollout and its archived copy, a Claude Code log in two project folders, a copied Harness log, or the older format generation Harness keeps beside an upgraded log, count once, from the newest copy.
- Sources parsed as whole files or account records replace a session's events from the start of the reading window's UTC day, or from where the reader's history starts when that is later — a database reader's last 8 days, Cursor's local midnight — so events a reader no longer returns stay until the ledger expires them; a missing file removes the sessions no listed file still holds. Usage an OpenCode, Kimi or Pi route holds under a hash of its provider and model, or its model and a hash of its provider, joins the route's id once a log names that route again. Their reports resolve overlapping logs first: the highest-priority log of a Grok or Copilot session, and one event per identity.
- After a collection pass that could not be saved, each source reads its stored positions again and writes what the ledger lost.
- Token events and totals keep 31 days, quota readings 30 days; expired rows are deleted, never rewritten. JSON caches of earlier versions are removed at start, and their quota histories are imported once.
