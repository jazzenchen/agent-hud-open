# Platform boundary

`NativePlatform` supplies local directories, client discovery, native process operations, file-change notifications and account-reader jobs. Core owns transcript parsing, session state, deduplication, SQLite accounting and derived metrics. Account adapters share one set of provider protocols, response parsers and scheduling rules across hosts.

`src/os/mod.rs` selects exactly one host implementation with compile-time `target_os`:

| Host module | Responsibilities | Verification |
| --- | --- | --- |
| `src/os/macos/` | Application Support and bundle paths, LaunchServices, original ledger locator, executable lookup, local process inspection, Finder reveal | Existing live Mac readers retained; this refactor is compile/fixture checked |
| `src/os/windows/` | USERPROFILE/AppData paths, native `.exe` lookup, hidden child-process flag, same-user process inspection, Credential Manager reads, Explorer reveal | Antigravity account discovery is read-only; broader interactive runtime remains unverified |
| `src/os/linux/` | XDG paths, desktop files, executable lookup, `/proc` executable identity, local process inspection, directory reveal | Runtime unverified; `ps`/`lsof` must be available for Antigravity |

Each host explicitly chooses `source_roots`. The current native Claude/Codex on-disk layouts are shared by `portable_cli_roots`; WSL, Windows Store and other container-specific layouts need their own host adapter. A detected installation does not imply that its sessions or account format have been migrated.

`NativePlatform::capabilities()` reports `validation`, per-reader verification, Antigravity availability and legacy-Mac-history availability. Windows/Linux portable Claude, Codex, Cursor and DeepSeek adapters remain usable: real successful results can become ready, while the platform remains `unverified`. This status is separate from authentication and quota availability. Windows engine connections currently require a real executable; detection of a `.cmd`/`.ps1` installation alone does not turn it into an account protocol connection.

Windows Codex discovery and account reading share one desktop installation locator. It reads the current user's registered `OpenAI.Codex` package manifest and locates the application's `resources/codex.exe`. Older Store builds relocate their runtime into `%LOCALAPPDATA%/OpenAI/Codex/bin/<16 hex digits>`; when present, the cache matching the registered binaries' official content hash takes priority over the package executable. Conventional desktop folders and other complete cached runtimes follow, with unmatched caches newest first; their order does not prove which version the desktop is running. The hash, layout and required companion executables follow official ChatGPT 26.1016.61520; staging/incomplete copies are ignored and no runtime is copied by Agent HUD. Package lookups are bounded and cached for five minutes (one minute when absent), with removed application entries invalidating the cache immediately. Discovery skips this lookup when client storage or a CLI already proves installation. Session roots still follow `CODEX_HOME`, otherwise `%USERPROFILE%/.codex`; a missing quota engine is separate from session ingestion. The package name is documented in [OpenAI's Windows deployment guide](https://learn.chatgpt.com/docs/enterprise/windows-deployment).

The account engine's JSON-lines protocol, bounded reader, deadlines, child ownership and cleanup stay in `accounts/engine.rs`. Provider identity, credentials, parsing and deduplication stay in `accounts/`; shell scripts do not make those decisions. Mac-specific dependencies such as `plist` are target-scoped in Cargo.toml. This crate contains no LAN/remote transport.

The editable command sources in `scripts/macos/`, `scripts/linux/` and `scripts/windows/` contain only fixed OS operations. They are embedded with `include_str!` at build time: edit the source and rebuild the corresponding host target. There is no runtime script-path setting or hot reload. Unix paths, UIDs and PIDs are separate argv values; Windows ancestry receives the caller PID through a dedicated environment variable. Values are never interpolated into script source. Process inspection is bounded and runs for account discovery or hook caller attribution, not on each HUD/input poll. Raw process output may contain a token and is never logged.

Explorer is invoked directly with one literal argv value. PowerShell `-Command` would reinterpret trailing text, so a shell wrapper is intentionally avoided for that operation.

Build/check the platform crate with the host toolchain and corresponding Rust target, for example from the repository root:

```sh
cargo check -p agent-hud-platform --target aarch64-apple-darwin
cargo check -p agent-hud-platform --target x86_64-pc-windows-msvc
cargo check -p agent-hud-platform --target x86_64-unknown-linux-gnu
```

These commands check this crate, not desktop packaging. A foreign target also needs its Rust standard library and native C toolchain for bundled SQLite/TLS dependencies. Windows builds and native tests run through the Windows GitHub workflow; interactive runtime qualification requires the machine acceptance checks in `docs/platform-builds.md`.


## Original Mac preference seed

`NativePlatform::legacy_preferences()` is a single read-only, Mac-only startup adapter. It reads the public `settings.v1`, `agents.v5` and `panelLayout.v2` JSON Data values from the original persistent defaults domain, and returns normalized `settings` plus `presentation`. Windows/Linux return no legacy seed. `Runtime::new_with_preferences(data_dir, read_accounts, initial_settings)` passes the app settings to Core's absent-file-only seed; the host seeds its own presentation owner only when its target is absent. Existing targets, including damaged ones, are not overwritten. Old defaults and credentials are never written.

The seed retains stable display UUIDs, saved current layouts, supported placement/glow values, public app preferences, original disabled live/reminder choices, provider order, quota row order and switches, and the hidden-account blacklist (including absent accounts). Third-party/unknown/private fields, credentials, previous layouts and drafts are discarded. The original four expanded-panel switches carry only their `false` values into every saved layout. Layout-specific order takes priority, then the original provider and row order. Hidden account identities remain a blacklist rather than becoming a list of today's visible accounts. Fully disabled API groups stay hidden without disabling collection; a mix of enabled/disabled model consumer rows inside an API balance still has no exact per-model balance representation. Alias identities not present in the acquired account facts cannot be guessed.

Pure isolated fixtures cover these conversions and preserve the main Runtime's immediate transcript reminder plus three 500ms signature followups. The reminder path uses Core's existing targeted reader/ledger and does not consume the ordinary watcher queue or list unrelated sources. No fixture touched real defaults or installed client configuration.

## Explicit hook ownership and native interaction

The canonical product host must explicitly delegate its fixed executable before hook installation. `set_enabled` changes only owned client entries using pure provider formatters and safe I/O; shutdown stops the channel and observers without uninstalling user configuration. Pi/OpenCode observers publish lifecycle facts to the same coordinator. Antigravity native permissions use only already-running, verified loopback services, revalidate the exact pending permission before a once-only response, and report uncertain delivery instead of claiming success. DeepSeek's native web question observer remains pending. No adapter starts a client or performs a new login.

The public `agent-hud-open` desktop calls `run_with_context` with default `HostOptions`, so `canonical_executable` is `None` and client-hook installation is unavailable, including in its NSIS package. The private product can delegate its approved installed executable; only that host can enable supported client hooks through Settings. Implemented Windows hook formats do not change this ownership boundary.

Windows hooks/local tools share the current-user/SYSTEM-only named-pipe primitive with remote clients rejected. Direct Windows executable/argument installation formats exist for Claude and Copilot, and the documented Windows command override is used for Codex; unsupported client contracts return explicit errors. Native compilation and test results are tracked by the Windows GitHub workflow; interactive hook behavior remains unverified. macOS and Windows Antigravity Desktop conversation navigation uses bounded local CDP on a running application and confirms the target before activating it. Windows validates the owning user, executable and port; its permission observer and control operations remain unsupported.

The shared Codex Desktop transport supports its Unix socket and Windows `\\.\pipe\codex-ipc` endpoint. Both use the same four-byte little-endian length, UTF-8 JSON, initialization and owner-routing messages. This contract was checked against the installed official ChatGPT 26.1016.61520 `app.asar` modules `application-network-startup-BG13czUt.js` and `src-CsH31EEu.js`; it is a desktop-client protocol, not the CLI app-server protocol. Windows validates the connected pipe server's TokenUser SID against the current user before sending, following [OpenAI's named-pipe peer validation](https://github.com/openai/codex/blob/9a8a85bc539325f2819dd0717f88b6ba6286495e/codex-rs/tui/src/ide_context/windows_pipe.rs), and bounds connection and I/O by an operation deadline. Synthetic Windows pipe fixtures cover framing, correlation, owner targeting, disconnects and timeouts. Interactive client behavior still needs Windows acceptance testing. The public Windows approval observer remains inactive; exposing this shared transport does not enable public approval collection or response controls.

After the existing Copilot quota consent gate, Windows reads GitHub CLI's generic Credential Manager entry through `CredReadW`, with a 32 KiB blob limit and no credential enumeration, login, refresh or write. The exact target is `gh:github.com:`: [go-keyring composes `service:username`](https://github.com/zalando/go-keyring/blob/master/keyring_windows.go), and [GitHub CLI retains an empty-username token entry](https://github.com/cli/cli/blob/trunk/internal/config/config.go). Windows first uses environment tokens, then a token in the selected `hosts.yml`, then this global keyring fallback; per-account keyring selection is not implemented. Plaintext `hosts.yml` follows [GitHub CLI's directory precedence](https://github.com/cli/go-gh/blob/trunk/pkg/config/config.go): `GH_CONFIG_DIR`, `XDG_CONFIG_HOME/gh`, then Windows `APPDATA/GitHub CLI`, then `~/.config/gh`. Captured Windows environment keys retain the OS's case-insensitive lookup semantics.

New private Windows IPC directories explicitly set the owner to the token's user SID at creation, including under an elevated token whose default owner may be Administrators. Existing foreign-owned directories are still refused. Windows CI tests use isolated directories and one uniquely named synthetic Credential Manager entry, deleted after its read; the implementation work does not access installed client credentials.
